# CJPlug 单端口收敛与双宿主合并方案

> 日期：2026-10-29（第二轮）
> 决策来源：D1 = **C 档**（双宿主合并 + 顺带重构）、唯一端口 = **5066**、工位机存量配置 = **硬切 + 迁移说明**
> 上一轮（第一轮）：《（已评审）CJPlug服务架构梳理与简化方案-20261029》—— 6 进程 → 2 进程，端口不变

## §0 结论先行

**本机进程 2 → 1，端口 5 → 1（5066），全量构建 0 错误，六面回归全绿。**

第一轮削掉的是三个薄壳服务（Dispatch / ElsaApi / Mcp，各 373~500 行），零代码搬迁、零风险。
第二轮合的是**两个各有独立 DI 底座、独立安全模型、独立启动管道的真宿主** —— 这一轮不是"去冗余"，是"合架构"，代价高一档，但换来的不只是省一个进程，还有三处跨端口隐式假设的消失。

| 进程（本机） | 2 | **1** |

| 内存（实测工作集） | Web 217MB + API 254MB | 单进程 |
| 构建 | 0 错误 | **0 错误** |

## §1 为什么单端口是"恢复原状"而不是"挤压"

原先 5 个端口里，功能本来就没有靠端口区分 —— `/mainHub`、`/elsa/api`、`/api/*` 全是路径。
**唯一真正依赖端口的是 MCP 挂在根路径**。把它挪到 `/mcp`，端口依赖就归零了。

### §1.1 路径分配表（已核对无重叠）

| 路径 | 归属 | 合并前端口 |
|---|---|---|
| `/`、`/{page}` | Blazor 页面 | 5066 |
| `/_blazor`、`/_framework/*` | Blazor circuit + 静态资源 | 5066 |
| `/elsa/api/*` | Elsa 引擎 | 5001 |
| `/mcp` | MCP 协议面（**唯一挪过位置的**） | 3001 |
| `/mainHub`、`/api/dispatch/*` | 调度 | 8686 |
| `/api/*`、`/swagger` | 27 模块业务 API | 8687 |
| `/webFiles/*`、`/plugconfig/*` | 静态文件 | 5066 |

### §1.2 选 5066 的依据

| 现有 5066 硬编码 | 处数 |
|---|---|
| Desktop 9 个 iframe URL + `MainWindow.xaml.cs` | 10 |
| `GlobalData.MainWebFileServerUrl` | 1 |
| AppHost `WithUrl` + 自动打开浏览器 | 2 |
| 用户书签 / README / 桌面快捷方式 | 不计 |

反方向的 8686/8687/5001/3001 共 86 处引用，但**其中 88 处走 `GlobalData.*` 常量** —— 改常量定义，引用自动跟随。两害相权，5066 的外部改动面最小。

## §3 双宿主合并的四个硬冲突与解法

| # | 冲突 | 实证 | 解法 | 结果 |
|---|---|---|---|---|
| 1 | **`/` 路由歧义** | 合并前：`5066/` → 200（178KB Blazor SSR）；`3001/` GET → **405**（MCP 端点匹配成功但只收 POST）。合并后同 pattern 两候选 ⇒ `AmbiguousMatchException` | `MapMcp("/mcp")`；3001 根路径由重写中间件转到 `/mcp` | ✅ |
| 2 | **Elsa 双栈共存** | Web 走 `AddElsaServicesForWeb()`（Studio 前端 + RemoteBackend，**不含引擎**）；API 走 `AddElsaServicesForApi()`（`AddElsa` + EF 带库引擎） | 两套注册都保留，Studio 仍走 HTTP 调自己的 `/elsa/api` | ✅ 全量日志**零 401/403** |
| 3 | **认证语义相反** | `PlugTempAuthHandler` **恒认证成功并赋 Admin**；而主 API 侧历来依赖"无认证身份"（第一轮 Phase 3 实测：全局启用授权会把按 Roles 过滤的菜单筛成空） | 判据从「端口」改为「路径」（`WebHostStartup.NeedsIdentity`），Handler 内也按同一判据返回 `NoResult` | ✅ 3 分组菜单完好 |
| 4 | **SignalR 5MB 上限丢失** | Web 是 `AddSignalR(o => o.MaximumReceiveMessageSize = 5MB)`（大工作流）；API 是裸 `AddSignalR()` | 合并时保留 5MB 版 | ✅ |

## §4 实施中踩到的坑（按危害排序）

### §4.1 `Duplicate endpoint name 'VncWebSocketProxy'` —— 会导致**全站 500**

**现象**：进程起来了、端口监听正常，但**所有请求 500**，日志里刷的是 Hub 连不上：

```
Failed to connect to SignalR hub: http://localhost:5066/mainHub
Response status code does not indicate success: 500
```

极易误判为"SignalR 合并失败"，实际根因是：

```
System.InvalidOperationException: Duplicate endpoint name 'VncWebSocketProxy'
  found on 'api/remote/vnc' and 'api/remote/vnc'. Endpoint names must be globally unique.
   at Microsoft.AspNetCore.Routing.EndpointRoutingMiddleware.InitializeCoreAsync()
```

**根因**：远程桌面代理端点由 `CJ.Plug.GuacamoleApi.RemoteDesktopApi` 映射，`MapRemoteDesktopApi()` 被调了两次 ——
Web 扩展里的（原 Web 宿主没有 `ConfigModuleApis()`，必须自己调）+ ApiServer 的 `ConfigModuleApis()`（27 模块扫描里已含它）。

**这个异常发生在 EndpointRoutingMiddleware 的 matcher 初始化阶段，不是单个请求的失败** —— 一旦抛出，本进程**每一个请求**都 500，包括 Hub 协商、MCP、静态资源。所以症状看起来像"Hub 坏了"，实际与 Hub 无关。

**处置**：`WebHostStartup.MapPlugWebHost()` 里**不**调 `MapRemoteDesktopApi()`；独立启动形态（薄壳 `Program.cs`）自己补一次。

> **教训**：合并带 `MapXxx()` 调用的宿主时，先清点"哪些 Map 会被两边的入口各调一次"。这类错误在启动日志里只是一条 `fail:`，很容易被后面的连锁 500 淹没。

### §4.2 既有 DI 生命周期缺陷（本轮被 Development 模式暴露）

```
Cannot consume scoped service 'CJ.Plug.DeekSeekIn.IDeepSeekService'
from singleton 'CJ.Plug.ProcessManageApi.Services.AiWorkflowBuilderService'
```

两个模块对同一接口注册了**不同生命周期**：

| 模块 | 注册 |
|---|---|
| `CJ.Plug.AI/ServiceCollectionExtensions.cs:15` | `AddScoped<IDeepSeekService, DeepSeekService>()` |
| `ProcessManageModule/ServiceCollectionExtensions.cs:45` | `AddSingleton<IDeepSeekService, DeepSeekService>()` |
| 同上 :46 | `AddSingleton<AiWorkflowBuilderService>()` ← 消费 Scoped |

后注册者胜出 ⇒ 最终是 Scoped ⇒ Singleton 的 `AiWorkflowBuilderService` 跨生命周期持有它。

**Development 下 `ValidateOnBuild=true` 直接启动失败；Production 下不验证，静默通过。** 这是既有问题，不是本轮引入（客户形态一直是 Production，所以从没暴露）。

**未修**（超出本轮范围，见 §7 待办 ①）。

### §4.3 `JavaScript interop calls cannot be issued at this time`（疑似既有噪音）

每个页面请求结束后在 `Renderer.Dispose` 抛一次，堆栈里**没有项目代码帧**，页面本身 200 且菜单完整。
判断为既有（组件 `Dispose` 里调 JS，SSR 阶段不允许），**未修**，见 §7 待办 ③。

### §4.4 启动方式：`ASPNETCORE_CONFIG_PATH` 必须是绝对路径

相对路径会 `PhysicalFileProvider` 抛 `The path must be absolute`，然后**静默回落**到输出目录的 `appsettings.json`（那是不带服务后缀的那份）。AppHost 传的本来就是绝对路径，只有手工命令行启动时要留意。

## §7 破坏性变更与迁移说明

### §7.1 必须人工处理的（客户现场）

| 对象 | 旧值 | 新值 |
|---|---|---|
| **工位机 `MainServerUrl`**（存在工位机 SQLite 配置里） | `http://<主服IP>:8686` | `http://<主服IP>:5066` |
| MCP 客户端 mcp.json（Cursor / Trae 等） | `http://<主服IP>:3001` | `http://<主服IP>:5066/mcp` |
| 防火墙 / 安全组 | 放行 8686、8687、5001、3001 | **只放行 5066** |

**工位机迁移步骤**：

1. 打开工位机上的「图站设置」界面（`StationSettingUI`）
2. 把「主服务器地址」从 `http://x.x.x.x:8686` 改为 `http://x.x.x.x:5066`（端口从 8686 改 5066，其余不变）
3. 保存后重启工位机服务
4. 验证：主服 `/StationManage` 页面能看到该工位机在线

> ⚠ **未改配置的工位机会静默失联**（连不上 8686，不会报错提示端口变更）。升级前请先通知现场。

### §7.2 无需处理的

- 浏览器书签、桌面快捷方式、Desktop 全部内嵌页面 URL（都是 5066）
- Elsa Studio 前端（`Backend:Url` 已在配置里改好）
- 数据库（无 schema 变更）

## §9 回退方式

**回退到第一轮形态（2 进程 / 5 端口）**：

1. `AppHost.cs`：取消 `webfrontend` 资源注释；`ApiServerContractUrls` 改回 `"http://*:8687;http://*:8686;http://*:5001;http://*:3001"`
2. `ApiServer/Program.cs`：`ContractUrls` 同上；恢复 `app.UsePlugPortGate();`；`MapMcp("/mcp")` → `MapMcp()`；恢复 3001 根路径重写中间件
3. `GlobalData.cs` 四个常量改回原端口
4. `appsettings.json` 的 `Backend:Url` 改回 `http://localhost:5001/elsa/api`

**回退到合并前的完全独立形态**：`AppHost.cs` 里 `sds` / `elsaapiserver` / `mcpserver` 三段也是注释保留的，一并取消注释即可。

> 薄壳 `HostWebServer/Program.cs` 走的是与合并形态**完全相同**的扩展代码，不是另一份实现 —— 所以回退不会引入行为差异。
