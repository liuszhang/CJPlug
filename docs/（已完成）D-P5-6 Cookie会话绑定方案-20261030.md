## 1. 落点变更：从「页面层」改到「HTTP 层」

### 1.1 原计划的死结

上一轮定的 A 方案是：在 `TryBuildStateFromHttpContext` 验签后补一句 `session.IsActive`。动手前核实代码，发现这条路必须付一笔额外代价：

```csharp
// CookieAuthStateProviderBase.cs:104（抽象方法，同步）
protected abstract bool TryBuildStateFromHttpContext(ClaimsPrincipal httpUser, string? token, out TState state);

// CookieAuthStateProviderBase.cs:28-33（同步包装）
public override Task<AuthenticationState> GetAuthenticationStateAsync()
{
    RestoreFromHttpContext();          // ← 同步调用
    return Task.FromResult(new AuthenticationState(User));
}
```

查 session 活性是 **DB 查询（异步）**，而这条链路整条是**同步**的。只有两种走法，都不好：

| 走法 | 代价 |
|---|---|
| 方法签名改 `Task<(bool, TState)>` | 牵动基类契约 + **3 个产品子类各改一处**（ThreeRole / AccountAuth / Ontology），且 `GetAuthenticationStateAsync` 的高频调用点要跟着改 |
| 同步阻塞 `.GetAwaiter().GetResult()` | Blazor Server 上的经典死锁姿势，不可接受 |

### 1.2 新落点：`OnValidatePrincipal`

Cookie 认证中间件**本来就提供了异步校验钩子**，而我们现在一个都没配：

```csharp
// CJCoreAuthServiceCollectionExtensions.cs:65-75 —— 现状
.AddCookie(options.CookieSchemeName, o =>
{
    o.LoginPath = options.LoginPath;
    o.LogoutPath = $"/{options.GroupPrefix.Trim('/')}/logout";
    o.AccessDeniedPath = options.LoginPath;
    o.ExpireTimeSpan = TimeSpan.FromHours(8);
    o.SlidingExpiration = true;
    o.Cookie.Name = options.CookieName;
    o.Cookie.HttpOnly = true;
    o.Cookie.SameSite = SameSiteMode.Lax;
    // ← 没有 o.Events：票据解出来是什么就认什么，一个字都不查
})
```

在这个钩子里判定失败 ⇒ `RejectPrincipal()` ⇒ `HttpContext.User` 变匿名 ⇒ 页面层 `CookieAuthStateProviderBase.cs:123` 的

```csharp
if (httpUser?.Identity?.IsAuthenticated != true) return;
```

**自然短路**。基类一行不用改，3 个子类一行不用改。

### 1.3 两种落点对比

| 维度 | 页面层（原计划 A） | **HTTP 层（本方案）** |
|---|---|---|
| 缺口位置 | `TryBuildStateFromHttpContext` | `AddCookie` 的 `OnValidatePrincipal` |
| 同步/异步 | 同步方法要异步查库 ⇒ 签名手术 | 钩子**原生 async** |
| 改动文件数 | 1 基类 + 3 子类 + 若干调用点 | **1 个装配器** |
| 覆盖产品 | 只覆盖走 Blazor 状态提供器的页面 | **HTTP 层判定，全部页面 / API / SSR 一次性覆盖** |
| 与 JWT 通道口径 | 各写一套 | **复用同一个 `ValidateAndCheckRevocationAsync`** |
| 架构割裂 | 保留（HTTP 层认 Cookie、页面层认 Token，两套口径） | **消除**（两层同源） |

> 架构割裂的具体表现：HTTP 层说"你登录着"（Cookie 验过），页面层说"你没登录"（无 token）⇒ 这就是上次排查"半登录"现象一路追到的根。落点换到 HTTP 层后，两层用同一份判据。

## 2. 凭据选择：用 token cookie 的 AT，不给 Cookie 加 jti

`OnValidatePrincipal` 拿到的 principal 里**没有 jti**（`ThreeRoleAuthAdapters.cs:203-212` 只写 NameIdentifier/Name/Role），所以"这枚 cookie 对应哪一条 session"无从判断。两条路：

| 方案 | 做法 | 问题 |
|---|---|---|
| Y：给票据加 jti | `IssueSessionCookieAsync` 里补一枚 jti claim | **存量 cookie 全都没有 jti** ⇒ 只能一律拒绝 ⇒ 全员强制重登一次（信创内网客户环境里这是可感知的运维事件） |
| **X：读 token cookie 的 AT（采纳）** | `.ThreeRole.Token` 里放的就是 **AT 原文**（`CJCoreAuthEndpoints.cs:343`），AT 自带 jti | 无 |

证据（`CJCoreAuthEndpoints.cs:329-349`，`/cookie` 与 `/embed-cookie` 共用这一段）：

```csharp
var claims  = cookieClaims.Build(...).ToList();                 // 票据：无 jti
var identity = new ClaimsIdentity(claims, options.CookieSchemeName);
await http.SignInAsync(options.CookieSchemeName, new ClaimsPrincipal(identity));
http.Response.Cookies.Append(options.TokenCookieName, token, ...);  // ← AT 原文，jti 就在里面
```

选 X 的附带收益：

1. **存量 cookie 零影响** —— token cookie 从上线第一天就有，老会话照样能解出 jti；
2. **口径对齐** —— 页面层本来就要求"两枚 cookie 齐备才 200"（P5.4 实测：只带 Auth 是 302，Auth+Token 才 200）。HTTP 层跟着要求 token cookie，两层判据终于一致；
3. **不新增 claim 语义** —— jti 留在 AT 里，票据继续只承载"我是谁 + 我有什么角色"。

## 3. 判据矩阵

| 场景 | 改动前 | 改动后 |
|---|---|---|
| 正常登录后访问页面 | 200 | 200（多一次验签 + 一次 session 核对，有缓存） |
| **登出（电路内 POST /logout）** | session 已撤，但**旧 cookie 仍 200 读到真实数据** | AT 核对失败 ⇒ **302 跳登录** |
| **登出（浏览器直连 GET /logout）** | cookie 已删，但 **session 没撤** ⇒ RT 仍可换新 AT | 一并撤销 session（§4.3） |
| **管理员停用/删除用户** | 旧 cookie 仍 8h 有效 | session 撤销后 ⇒ **302** |
| 有 Auth cookie、无 token cookie | 200（HTTP 层）→ 302（页面层），**半登录** | **302**（HTTP 层直接拒，不再产生半登录） |
| AT 自然过期（60 min） | 302（页面层验签失败） | 302（HTTP 层判定，跳变更早） |
| 匿名访问公开页 | 200 | 200（无 cookie ⇒ 钩子不触发） |
| 静态资源（`_framework/*`） | 200 | 200（白名单跳过，见 §4.1） |
| 电路内交互（SignalR） | 不受影响 | 不受影响（连接建立后不再走 HTTP 认证；写操作另由重签链路兜底） |

## 4. 实现设计

### 4.1 `OnValidatePrincipal` 主体

改写 `CJCoreAuthServiceCollectionExtensions.AddCJCoreAuth` 里 `AddCookie` 的配置（其余属性一字不动）：

```csharp
.AddCookie(options.CookieSchemeName, o =>
{
    /* …现有 LoginPath / LogoutPath / AccessDeniedPath / ExpireTimeSpan /
       SlidingExpiration / Cookie.Name / HttpOnly / SameSite 全部保留… */

    o.Events = new CookieAuthenticationEvents
    {
        // 票据解出来只说明"这枚 cookie 是本站签发的"，不说明"这枚 cookie 现在还该被认"。
        // 判据与 JWT 通道同源：验签 + 真撤销（ValidateAndCheckRevocationAsync）。
        OnValidatePrincipal = async ctx =>
        {
            // ① 静态资源不校验：不承载业务数据，且量最大（每请求查库会把真撤销的成本放大到无意义）
            if (IsStaticAsset(ctx.Request.Path)) return;

            // ② 凭据 = token cookie 里的 AT；缺失即拒（双 cookie 依赖，与页面层同口径）
            var token = ctx.Request.Cookies[options.TokenCookieName];
            if (string.IsNullOrWhiteSpace(token)) { ctx.RejectPrincipal(); return; }

            // ③ 请求已中止：不发起查询，也不改判定（结果无人接收）
            if (ctx.RequestAborted.IsCancellationRequested) return;

            var jwt = ctx.HttpContext.RequestServices.GetRequiredService<CJCoreJwtTokenService>();
            CJCoreTokenPayload? payload;
            try
            {
                payload = await jwt.ValidateAndCheckRevocationAsync(token, ctx.RequestAborted);
            }
            catch (OperationCanceledException) when (ctx.RequestAborted.IsCancellationRequested)
            {
                return;   // 与 JWT 侧 OnTokenValidated 同一条收口规则（否则 EF/Npgsql 取消会刷成 ERR 堆栈）
            }

            if (payload is null) ctx.RejectPrincipal();
        },
    };
})
```

**只 `RejectPrincipal()`，不删 cookie。** 理由：`Response.Cookies.Delete` 的 `Path`/`Domain` 必须与写入时逐字一致才生效，而 token cookie 是手工 `Append` 的（`CookieOptions` 未显式给 `Path`），删不干净的失败模式很隐蔽；`RejectPrincipal` 已经达到"认证失败"的语义，登录时新票据自然覆盖旧值。

`IsStaticAsset` 判据（前缀白名单，不用扩展名猜）：

```
/_framework/  /_content/  /_blazor  /favicon.ico  /css/  /js/  /lib/
```

拒绝时**不写 302**：`RejectPrincipal` 只让 `User` 变匿名。带 `[Authorize]` 的页面由授权中间件正常 Challenge（302 到登录页）；静态资源没有 `[Authorize]`，照样 200 返回 —— 不会出现"JS 请求收到一段登录页 HTML"那类崩法。

### 4.2 校验结果缓存

`OnValidatePrincipal` 对**每一个带 cookie 的请求**触发。剥掉静态资源后剩下的主要是页面导航，量可控；但 `ValidateAndCheckRevocationAsync` 要查库，仍应缓存。

| 项 | 取值 |
|---|---|
| 容器 | `IMemoryCache`（`TryAddSingleton`，宿主已注册则复用） |
| 键 | `ck:jti:{jti}` |
| 值 | 仅缓存**通过**，不缓存失败 |
| TTL | **待拍板**（§8 D1：0 / 30s / 60s） |
| 主动清除 | 登出时 `Remove`（§4.3） |

失败必须每次实查：撤销是安全事件，缓存失败会让"刚恢复的用户"被继续拒。

### 4.3 顺带修：`GET /logout` 不撤销会话

`CJCoreAuthEndpoints.cs:166-171` 现状：

```csharp
g.MapGet("/logout", async (HttpContext http) =>
{
    await http.SignOutAsync(options.CookieSchemeName);
    http.Response.Cookies.Delete(options.TokenCookieName);
    return Results.Redirect(options.LoginPath);
});
```

只删 cookie，**不碰 session** ⇒ 登出后 RT 仍有效，可换出全新 AT。与 `POST /logout`（第 148-163 行，有 `RevokeSessionAsync`）行为不一致。

修法：从 token cookie 取 AT → `ValidateToken` → `RevokeSessionAsync(jti)` → 再删 cookie；同时 `cache.Remove($"ck:jti:{jti}")`。

## 8. 决策点

### 已定

**D1 = A（30 秒缓存）** —— 2026-10-30 00:15 拍板。泄漏窗口 8h → ≤30s（主动登出为 0）；稳态查库降为「每用户每 30s 一次」，比 JWT 侧每请求查低两个数量级。

配套约束：登出必须主动 `Remove` 缓存键（§4.3 已实现），否则"主动登出"也要等满 30s。

| # | 结论 | 依据 |
|---|---|---|
| D1 | 校验结果缓存 **30 秒** | 见上 |
| D2 | 静态资源白名单跳过校验 | 不承载业务数据；不跳过等于把最大流量纳入查库 |
| D3 | 拒绝时只 `RejectPrincipal`，不删 cookie | `Response.Cookies.Delete` 的 Path 匹配坑，收益不抵风险 |
| D4 | 不给 Cookie 票据加 jti claim | 存量 cookie 全员失效，需强制重登 |
| D5 | `GET /logout` 一并撤销 session | 与 `POST /logout` 对齐，堵 RT 换发口子 |

### ⚠ 判据坑（本次踩到，必须记住）

**第一版 V2 误判为"失败"**：用 `GET /` 做判据 → 登出后仍 200，一度以为钩子无效。

两处错误叠加：

1. `/` 是 `HomePage` 的**公开页**（无 `[Authorize]`），匿名访问本来 200 —— 不能用它测"是否被踢"。
2. 页面里 grep 到的 49 个 `Admin` 全是**类名**（`ThreeRoleAdmin` / `ModuleAdmin` / `CJCore.Modules.ModuleAdmin.*`），不是用户身份数据。

正确判据：**用带 `[Authorize]` 的页面（`/process/{id}/execute`），看 302 目标**。日志侧的佐证是 `dbug: [Cookie票据] 拒绝认证：… path=/` 确实按次出现。

### 新发现的存量缺陷（非本轮引入）

`GET /` 首页在**登录态与匿名下都**渲染出 8 处异常堆栈，根因同一个：

```
System.InvalidOperationException: The property 'MarketPlug.UsersCount' cannot be marked
as nullable/optional because the type of the property is 'int' which is not a nullable type.
  at Microsoft.EntityFrameworkCore.Metadata.Internal.Property.SetIsNullable(...)
  → [CjAutoMigration] EF 增量计划构造失败，回退自研 diff 完整路径（F1）
```

EF 模型把 `int` 属性声明成了可空 ⇒ 迁移器每次都回退到自研 diff 路径，首页渲染也跟着吐堆栈。属独立缺陷，建议单独立项（与 D2「Development 环境起不来」同批处理）。
