## 1. 现状（调研结论）

### 1.1 注册高度收口：一个文件、三段

`src/modules/CJ.Plug.ModuleConfig/ModuleConfig.cs`（模块注册唯一入口）：

| 段 | 方法 | 与四模块相关的行 |
|---|---|---|
| ① UI 侧 | `ConfigModulePageServices` | `AddUserManagePageModuleServices()` / `AddAuthModulePageServices()` / `AddAuditModulePageServices()` / `AddLoginModulePageServices()` |
| ② DI 侧 | `ConfigModuleApiServices` | `AddUserManageModuleApiServices()` / `AddAuthModuleApiServices()` / `AddAuditModuleApiServices()` |
| ③ 端点侧 | `ConfigModuleApis` | `AddLoginModuleApi()` / `AddAuditModuleApi()` / … |

**关键机制**：`FrameworkRoutes` 的 `AdditionalAssemblies` 由 `IEnumerable<IModule>` 反推 ⇒ **不注册 `IModule`（① 段）该模块的所有 `@page` 路由与菜单/AppBar 项同时消失**。这正是「摘入口」的天然开关，不需要逐页处理。

### 1.2 依赖核查（摘 UI 注册是否安全）

| 核查项 | 结论 |
|---|---|
| `IUserManageService` / `IAuditService` / `IAuthService` 被四模块外引用 | **0 处**（grep 全仓，排除自身模块）⇒ 摘 UI 注册不破坏业务 |
| `AddIdentity` 调用 | **仅 1 处**：`LoginModule/CJ.Plug.Login/LoginServiceCollection.cs:40`，位于 `AddLoginModuleApiServices` 内，而该方法在 `ModuleConfig.cs:86` **早已被注释** ⇒ **当前运行时没有 Identity scheme** |
| 三员对等页面是否就位 | ✔ `/three-role/system`（用户/角色/部门）、`/three-role/auth`、`/three-role/audit` 已上线且菜单已在（实测菜单 27 项含新旧两套） |

### 1.3 一个必须修正的历史结论（A.2 第 3 条的 `AddIdentity` 抢 scheme）

P5.1 期实测日志出现过 `AuthenticationScheme: Identity.Application was not authenticated`，据此在 `WebHostStartup.cs:376-391` 写了"LoginModule 的 `AddIdentity` 抢默认 scheme"的结论，并加了 `AddOptions<AuthenticationOptions>` 抢回段。

**现今取证**：`AddIdentity` 的唯一调用点所在方法已被注释，CJCore 全仓无 `AddIdentity/AddIdentityCore/AddDefaultIdentity` ⇒ **当前不可能有 `Identity.Application` scheme**。因此：
- 该抢回段**本轮不动**（保留无害，且能防"日后有人恢复 ModuleConfig:86 的注释"这类回退）；
- 结论按「**证据不足，待复核**」记录，不写成既成事实。真正的形态是：`AddCJCoreAuth` 设 `DefaultScheme=ThreeRolePolicy / DefaultChallengeScheme=ThreeRoleCookie`，宿主不干预也能工作。

### A.4 一条判据陷阱（与 P5.5 同源）

CJPlug 的 `NotFoundPage` 是 catch-all（`/{**path}`），**未匹配路由返回 HTTP 200 + 正文「404 - 页面未找到」**。所以 `curl -w %{http_code}` 恒为 200，**必须断言正文**。本轮先用 status 判定得出"旧路由仍 200"，改按正文后确认全部 404。
