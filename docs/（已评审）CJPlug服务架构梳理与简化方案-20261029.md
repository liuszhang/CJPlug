# （待评审）CJPlug 服务架构梳理与简化方案-20261029

> 触发：用户提出「感觉拆成这么多个单独的服务有点过度设计了，管理起来也不方便」。
> 本文只做**梳理 + 方案**，不改代码。所有结论可回溯到文件行号。
> 关联文档：《（设计中）CJPlug接入CJCore实施计划-20261029.md》

---

## 0. 结论先行

| 判断 | 结论 |
|---|---|
| 是否过度设计 | **是，但只过度了 3 个**。6 个进程里有 3 个（DispatchServer / ElsaApiServer / McpServer）没有独立的物理理由，其中 **DispatchServer 是最典型的伪拆分**（全服务 373 行代码，却占 1 个进程 + 1 个端口 + 1 份配置 + 1 套桌面端探测逻辑） |
| 真正的物理边界 | 只有 2 条：**工位机**（跨机器、要跑 uvnc/性能计数器/cmd）和**浏览器 UI**（Blazor Server）。其余都是"同一台机器上被拆开的进程" |
| 收益在哪 | 不是性能，是**可运维性**。当前 11 个端口硬编码在桌面端、6 份配置文件腐化到 4 份写错端口、5 个进程共享同一输出目录导致"任一在跑就锁构建"（本轮已反复踩 MSB3027） |
| 能不能简化 | **能，且第一步零业务风险**。关键手段：**Kestrel 多端点** —— 合并进程但保留原端口，工位机与外部 MCP 客户端的连接串**一个字都不用改** |
| 建议目标 | 6 进程 → **3 进程**（主宿主 + Web + 工位机），端口 11 → 6 或更少 |
| 与 CJCore 主线的关系 | **服务拆分是 CJCore 模块化的历史竞争品**。P4/P5 正在把 CJPlug 业务收进 CJCore，两套边界会打架 ⇒ 简化服务本质上是「让 CJCore 模块成为唯一边界」的前置清理 |

推荐路线：**A（运维归一，0 风险）→ B（合 DispatchServer，低风险）→ 视效果再决定 C（合 Elsa/MCP）**，三步各自可独立验收、可独立回滚。

### 1.3 部署形态

- 客户现场：**单机内网 + ARM64 信创 + 离线 tar.gz**（既有部署约束）。
- 即：6 个进程挤在一台机器上，共用一个发布目录、共用一份底层 SQLite 数据文件。

## 2. 过度设计的 7 条实证

| # | 证据 | 位置 | 代价 |
|---|---|---|---|
| 1 | **工位心跳要绕一圈写库**：Hub 收到 `SendStationStatus` 后，`new HttpClient()` 反向调 ApiServer 的 `api/Station/CreateStation` | `DispatchServer/Hub/MainHub.cs:21-45` | 多一次网络往返、多一个失败点、`new HttpClient()` 有 socket 耗尽隐患；合并即退化为一次方法调用 |
| 2 | **MCP 发布通知走 3 跳**：ApiServer → HTTP → DispatchServer → SignalR → McpServer | `ApiServer/Hubs/SignalRMcpToolChangeNotifier.cs` + `DispatcherApi.cs:20` | 通知链任一环断则工具不刷新；本轮已实测「McpServer 先于 ApiServer 启动 ⇒ 永远 0 工具且不自愈」 |
| 3 | **6 份 appsettings，4 份 Kestrel 写错** | ApiServer / ElsaApiServer / HostWebServer / StationApiServer 全部写成 `http://*:5066` | 裸启动必撞端口；只能靠 AppHost 注入环境变量兜底 ⇒ 任何"手工起服务"的场景都不可靠（本轮 McpServer 的 5066 冲突即同源） |
| 4 | **5 份 appsettings 内容 100% 相同**（1583B / 10 键，ElsaApiServer 只多 1 段 `Mazhifu`） | `src/**/appsettings.json` | 每份都带着它根本不用的 Guacamole / RabbitMq / Backend 配置；改一处要同步 5 处 |
| 5 | **11 个端口硬编码在桌面端** | `Desktop/Services/AppHostLauncher.cs:240` | 含已下线的 5010，端口规划变更必须改客户端并重新发版 |
| 6 | **共享输出目录 ⇒ 任一服务在跑就锁死构建** | 全部服务 `workingDirectory = servicesDir` | 本轮已反复踩：MSB3027/MSB3021，必须停全部服务才能构建；开发迭代成本被显著放大 |
| 7 | **半残注册**：ElsaApiServer 复制了 `ConfigModuleApiServices()`（27 个模块服务）但**没注册 MainDbContext** | `ElsaApiServer/Program.cs:52` vs `ApiServer/Program.cs:87` | 注册了用不了的依赖；一旦有人在此进程 map 模块端点即启动即崩 |

附带一条**潜在风险**（非本轮引入）：ApiServer 与 ElsaApiServer 两个进程同时打开 `main.db`（`ConnectionStrings:PlugDb`）。SQLite 的 `Cache=Shared` 只在同进程内共享缓存，跨进程仍是文件锁 ⇒ 高并发写有 `database is locked` 风险。合并进程会**消除**这个风险。

## 3. 逐服务评估矩阵

| 服务 | 它"独立"的理由 | 是硬约束还是历史? | 合并成本 | 建议 |
|---|---|---|---|---|
| **DispatchServer** | ① 工位机只连 8686，防火墙只开这一个口 ② 无 DB 依赖，DB 挂了它还能报在线状态 | **纯历史**。①可用 Kestrel 多端点保留 8686 解决 ②价值极低（在线表本身就在内存，进程重启即丢） | **低**：搬 6 个文件进 ApiServer / 抽类库；Hub 回环改进程内调用 | ✅ **合并（首选）** |
| **ElsaApiServer** | 带 EF Core 的 Elsa 运行时（`main-elsa.db`），需独立重启 | **半个历史**。ApiServer 已 `AddElsa`（`ConfigElsaServicesWithOutDB`），说明 Elsa 与主 API 的 DI **本来就能共存** | **中**：需把 ApiServer 的 withoutDB 换成 withDB，Elsa 的 hosted service 会进 API 进程（启动时间、内存待实测） | ⚠ **第二优先，需实测** |
| **McpServer** | 对外 MCP 面（Cursor/Trae 直连 3001）；`app.MapMcp()` 一行即可挂到任意宿主 | **弱**。CJCore 自身设计里 `McpSurface` 就规划了 `/mcp`、`/mcp/device` 挂进主宿主 | **低**：`app.MapMcp()` + 保留 3001 端点 | ⚠ **可合，但建议最后做**（对外协议面独立更利于限流/暴露控制） |
| **HostWebServer** | Blazor Server UI，且已是 CJCore 框架宿主（`MapCJCoreRazorComponents`） | **是**（UI 与 API 的依赖谱系差异大：它引 18 个项目，含 CJCore.Framework.UI） | **高**：会把 CJCore 框架依赖灌进纯 Minimal API 进程 | ❌ **不合**（保留） |
| **StationApiServer** | 运行在**工位机**上：uvnc、性能计数器、cmd 执行、独立端口可配（`--port` / SQLite 配置） | **是，物理边界** | 不可行 | ❌ **必须独立** |
| **ElsaStudio(5010)** | — | **已下线** | — | 🧹 **从桌面端端口列表清理** |

## 4. 三档方案

### 4.1 A 档：运维归一（不动进程，0 业务风险）

| 项 | 做法 |
|---|---|
| 配置归一 | 6 份 appsettings 收敛为 `SharedAppSettings.json`（仓库根已有此文件！）+ 每服务仅保留差异段；删掉各份里用不到的 Guacamole/RabbitMq/Backend |
| 端口归一 | 各 appsettings 的 Kestrel 统一**删除**（不再允许配置里写死端口），端口**只由 AppHost 环境变量给出**；裸启动场景改用 `--urls` |
| 端口清单单一真理源 | 桌面端 `allPorts` 改为从 AppHost 的 `ResourceStrings` / 一份 `ports.json` 读取，去掉 5010 |
| 构建解耦 | 各服务输出到**各自** `Services/{项目名}/` 子目录（或保留共享目录但构建时用 `-p:UseAppHost` 差异目录），消除"任一在跑就锁构建" |
| 文档修正 | README「8 个微服务」改为实际拓扑 |

- 收益：立刻消除本轮反复踩的构建锁坑 + 端口配置腐化；**不动任何业务代码**。
- 工作量：小（半天内）。
- 风险：几乎为零；回滚 = 恢复 6 份配置。

### 4.2 B 档：合并 DispatchServer（推荐作为第一步实质合并）

目标：`sds` 进程消失，`apiservice` 同时监听 **8686 + 8687**。

| 改动点 | 具体做法 |
|---|---|
| 代码搬迁 | DispatchServer 的 6 个文件（373 行）移入 ApiServer（或抽 `CJ.Plug.Dispatch` 类库被 ApiServer 引用） |
| Hub 挂载 | ApiServer 加 `AddSignalR()` + `MapHub<MainHub>("/mainHub")` + `MapDispatcherApi()` |
| 双端口 | ApiServer 的 Kestrel 配 2 个命名端点：`Http=8687`、`Dispatch=8686`（AppHost 传两个环境变量） |
| 回环消除 | `MainHub.SendStationStatus` 里的 `new HttpClient()` → 直接注入 `IStationService` / DbContext |
| 通知链收敛 | ApiServer 的 `SignalRMcpToolChangeNotifier` 改为直接 `IHubContext<MainHub>` 广播，**3 跳降为 1 跳** |
| 自连消除 | `HubConnectionManagerService` 在 Dispatch 内是"连自己 8686"取在线表；合并后改进程内直读 `StationList` |

- 收益：进程 6→5；消除 1 条 HTTP 回环 + 1 条三跳通知链；少 1 份配置、1 个端口探测项。
- 风险：**低**。工位机连接串（`localhost:8686`）**完全不变**（双端口保留契约）。
- 回滚：AppHost 把 `sds` 资源加回来即可（代码在同一个仓库，抽类库则两处都能挂）。
- 工作量：约 1 天（含冒烟）。

### 4.3 C 档：单主宿主（合 Elsa + MCP）

目标：`apiservice` 同时监听 **8686 + 8687 + 5001 + 3001**，进程 6 → **3**（主宿主 / Web / 工位机）。

| 子项 | 风险 | 前置条件 |
|---|---|---|
| 合 ElsaApiServer | **中**：Elsa 的 `UseWorkflowRuntime(ef)` + 调度器 hosted service 进入 API 进程，启动时间与内存需实测；`ConfigElsaServicesWithOutDB` → `ConfigElsaServices` 需替换（两套 `AddElsa` 不能并存） | 先做 B；实测 API 启动时间 < 15s、内存增量 < 300MB |
| 合 McpServer | **低**：`app.MapMcp()` 一行 + 保留 3001 | 先做 B |
| 桌面端/AppHost | 端口映射与启动顺序全部重排 | 前面两项完成 |

- 收益：进程 6→3、端口 11→6、内存量级从 ~500MB 降到 ~250MB（数量级估算，非实测）、日志/崩溃点减半。
- 风险：**中**。Elsa 与主 API 共进程后，工作流执行异常可能影响 API 可用性；需保留"拆分回退开关"（AppHost 配置项 `MergeElsa=false` 即回到独立进程）。
- 工作量：约 2-3 天（含回归）。

| 维度 | A 运维归一 | B 合 Dispatch | C 单主宿主 |
|---|---|---|---|
| 进程数 | 6 | 5 | **3** |
| 端口数 | 11（清理后 9） | 9 | **6** |
| 业务代码改动 | 0 | 373 行搬迁 + 2 处回环改造 | B + Elsa/MCP 合并 |
| 可独立验收 | ✅ | ✅ | ✅ |
| 可回滚 | ✅ | ✅ | ⚠ 需保留开关 |
| 解决"构建锁" | ✅ | — | ✅（进程少了） |
| 解决"三跳通知" | ❌ | ✅ | ✅ |
| 解决"跨进程共写 SQLite" | ❌ | 部分 | ✅ |

## 5. 硬约束（哪些**不能**合，避免下次又有人提）

| 约束 | 原因 |
|---|---|
| StationApiServer 必须独立进程、独立机器 | 它跑在工位机上（uvnc-portable、性能计数器、cmd 执行、可配端口），与服务器不是同一台 |
| HostWebServer 暂不合进 API | 它是 CJCore 框架宿主（引 18 个项目含 `CJCore.Framework.UI`），合进去会把 Blazor/CJCore 依赖灌进纯 Minimal API；且 UI 与 API 的发布节奏不同 |
| MCP 对外面若要独立暴露/限流，则保留独立端口 | 即使进程合并，`3001` 应作为**独立监听端点**保留，便于反向代理层单独控制 |
| 合并后端口契约必须保留 | 工位机 `StaticData.MainServerUrl`、MCP 客户端（Cursor/Trae）、Desktop 的 URL 全部写死在这些端口上 ⇒ **端口是外部契约，不是内部实现** |

## 6. 推荐路线（分三步，每步独立验收）

| 步骤 | 内容 | 验收判据 | 回滚 |
|---|---|---|---|
| **Step 1 = A** | 配置/端口/构建目录归一 + 文档修正 | 裸启动任一服务不撞端口；构建时不必停全部服务 | 恢复 6 份配置 |
| **Step 2 = B** | DispatchServer 并入 ApiServer（双端口 8686+8687） | 工位机能正常上线/心跳/取任务；MCP 发布通知 1 跳到达；`/api/dispatch/*` 行为不变 | AppHost 加回 `sds` 资源 |
| **Step 3 = C（可选）** | 合 Elsa / MCP；进程降到 3 | API 启动 <15s、内存增量 <300MB、工作流执行回归通过 | `MergeElsa=false` / `MergeMcp=false` 开关 |

> ⚠ Step 2 与进行中的《CJPlug 接入 CJCore》P4（41 表归一）/P5（身份替换）**有交叠**：P4 会动 `MainDbContext`，Step 2 会动 `Program.cs` 注册。建议 **Step 1 先做（零冲突）**，Step 2 排在 P4 之后，避免同一个 `Program.cs` 两处大改互相踩。

**D1：先做哪一档？**

## A.3 三个关键技术决策

1. **端口从配置移到代码**。共享输出目录 + JSON 按键深度合并 ⇒ 任何服务读 `appsettings.json` 都会继承别人的端点。改造中实测：Web 宿主读主宿主的 4 个端点后去抢 8687，直接启动失败。
2. **端口级路由闸门**。Kestrel 多端点共享同一张路由表，若不拦截，3001（对外 MCP 面）会暴露全部 27 个模块 API。`PlugPortGate` 按端口白名单恢复原语义。
3. **MCP 工具延迟刷新**。合并后 `RefreshAsync` 变成"进程通过 HTTP 调自己"，在 `app.Run()` 之前必然失败；改由 `BackgroundService` 延迟 3s 执行，并顺带补了 60s 周期兜底（原实现只在启动刷一次，先起 McpServer 就永远 0 工具）。
