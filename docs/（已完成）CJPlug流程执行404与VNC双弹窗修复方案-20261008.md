## 2. 根因一：执行整个流程失败（真因是 401，症状是 404）

**根因一句话**：Elsa 3.9 把「内置管理员 API Key」也改成**未显式配置 = 全拒**，而 `ElsaApiClient`（流程保存/执行/历程都走它）只带 `Authorization: ApiKey 00000000-0000-0000-0000-000000000000`（硬编码占位）⇒ 引擎侧每个管理端点恒 **401**；保存与执行两处**都不检查状态码** ⇒ 静默失败 ⇒ 响应头没有 `x-elsa-workflow-instance-id` ⇒ 实例 ID 为 `null` ⇒ 拿这个 null 去拼历程 URL，得到 `/elsa/api/workflow-instances//journal`（空段）⇒ 路由匹配不上 ⇒ **404** ⇒ `EnsureSuccessStatusCode()` 抛 `HttpRequestException` ⇒ 冒到 `ErrorBoundary`，整页报错。**真正的 401 被一个假 404 完全掩盖。**

### 2.1 只读实测证据（对运行中的安装态引擎取证）

| # | 探针 | 实测值 | 结论 |
|---|---|---|---|
| E1 | `GET /elsa/api/workflow-definitions` + `Authorization: ApiKey 00000000-…` | **401** | 客户端现役凭据被拒 |
| E2 | 同一 URL 换 `PATCH` | **405** | 路由**存在** ⇒ E1 的 404/401 不是"接口没了" |
| E3 | `PATCH /elsa/api/workflow-definitions/zzz/execute`、`PATCH /elsa/api/workflow-instances/zzz/journal` | **405 / 405** | 保存、执行、历程三条路由都在 |
| E4 | `POST /elsa/api/identity/login`，口令＝`Base64(SHA256("CJPlug.Elsa.Admin\|" + elsa-signing.key))`、用户 `admin` | **200** + `isAuthenticated=true` + 有 `accessToken` | 管理员 JWT 通道可用，且**任一进程按同源规则算出的口令都能登录** |
| E5 | `GET /elsa/api/workflow-definitions` + `Authorization: Bearer <E4 的 accessToken>` | **200** | JWT 通道对同一端点是被接受的 |
| E6 | `POST`/`GET /elsa/api/workflow-instances//journal`（空实例 ID） | **404** | 复现 P1 的那次 404，坐实失败链最后一跳 |

### 2.2 源码/文档级证据（Elsa 3.9.0）

| # | 证据 | 结论 |
|---|---|---|
| E7 | `Elsa.Identity.xml`，`DefaultAuthenticationFeature.UseAdminApiKey()`（无参重载） | 原文：*"Configures the API key provider type to `AdminApiKeyProvider`. **The provider denies all keys unless configured.**"* ⇒ 无参调用 = 拒绝一切 key |
| E8 | 同文件 `UseDevelopmentAdminApiKey()` | 原文：*"Enables the all-zero development admin API key. **Do not use in production.**"* ⇒ 全零 key 需显式启用，且官方标注生产禁用 |
| E9 | `ElsaExtensions.cs:117` 现役写法 | `elsa.UseDefaultAuthentication(auth => auth.UseAdminApiKey())` = **无参** ⇒ 正是 E7 的"全拒"形态 |
| E10 | `GlobalData.cs:17` + `DispatchServer.GetElsaEngineApiKey()` + `ElsaApiClient.cs:40` | key 值来源是硬编码全零占位，DispatchServer 原样返回，客户端原样发送 ⇒ E1 必然 401 |
| E11 | `ElsaExtensions.cs:73-113`（同页修复的上一份方案） | Studio 侧已显式引导管理员用户 + 替换 `IJwtAccessor` 自动登录取 JWT ⇒ **只有 Studio 那条通道被修好，`ElsaApiClient` 这条被漏掉**（这就是"组件库正常、执行流程却失败"的分野） |

### 2.3 失败链（P1 逐步还原）

```
① ExecuteFlow (MyDiagramDesignerWrapper.razor:333)
     ├─ MainApiClient.SubmitExecute(...)              → ApiServer 正常
     └─ ElsaApiClient.ExecuteWorkflowWithExecuteSetting(FlowchartJson, ExecuteSetting)
②        └─ SaveWorkflowFromJsonAsync → DeleteByDefinitionIdAsync(401,吞掉) → SaveWorkflowAsync(POST,401,**不看状态码**)
③        └─ ExecuteAsync → POST …/{definitionId}/execute(401,**不看状态码**)
              ⇒ 响应头无 x-elsa-workflow-instance-id ⇒ WorkflowInstanceId = null
④ PrepareAndExecuteWorkflow
     └─ GetJournalAsync(null) → GET /elsa/api/workflow-instances//journal → **404**
          ⇒ EnsureSuccessStatusCode() 抛 HttpRequestException
⑤ 异常冒到 MainLayout 的 ErrorBoundary ⇒ 整页「出错了！…404 (Not Found).」
```

> 「单个节点能成功」正好是该诊断的对照项：单节点走 `MainApiClient.ExecutePlug` → ApiServer `/api/plug` → 图站，**完全不经过 Elsa 引擎**。

## 3. 根因二：单节点执行弹出两个 VNC 窗口

**根因一句话**：图站绑定端点的"冗余绑定"判据用 `string.Equals(current.ProcessName, request.ProcessName)` 直接比，而 StationAgent 上报的进程名是 **`null`**（工具未配置「远程查看进程名」）、VncViewer 从地址栏回绑带的是**空串 `""`** ⇒ `null ≠ ""` ⇒ 把"回绑"误判成"新目标" ⇒ **第二次广播 `VncPidReady`**；前端去重键是 `sessionKey ?? "ip|pid|name"`，两次的键形状不同 ⇒ `window.open` 两次 ⇒ 两个窗口。第二个窗口自身回绑时 `"" == ""` 被判冗余 ⇒ 不再继续，**所以正好两个、不会无限**。

### 3.1 实机日志证据（图站 `StationLogs\log20261008.txt`）

```
10:11:05.932  VNC 窗口绑定已设置: PID=34012, 进程名=null, 会话=fc56     ← StationAgent 主A绑定
10:11:05.947  已绑定单窗口VNC目标: Notepad(PID=34012)
10:11:05.939  {"StationIp":"192.168.3.196","Pid":34012,"ProcessName":null,"SessionKey":"fc56"}   ← 第 1 次 VncPidReady → 弹窗 1
10:11:07.209  VNC 窗口绑定已设置: PID=34012, 进程名=,    会话=fc56     ← VncViewer 回绑（请求 sessionKey=null；registry 保留旧会话键）
10:11:07.211  {"StationIp":"192.168.3.196","Pid":34012,"ProcessName":"","SessionKey":null}        ← 第 2 次 VncPidReady → 弹窗 2
10:11:08.248  VNC 窗口绑定已设置: PID=34012, 进程名=,    会话=fc56     ← 第 2 个窗口回绑，此时 ""=="" 判冗余，不再通知
```

同一个上午 00:05:58 那次两条载荷的 `SessionKey` **都是 null**，前端两个键都退化成 `ip|pid|name` ⇒ 被去重 ⇒ 只弹一个 ⇒ 解释了该缺陷为何"时有时无"。

### 3.2 代码级判据分析

| # | 位置 | 事实 |
|---|---|---|
| E12 | `RemoteDesktopApi.BindWindowTarget`（改前） | `string.Equals(current.ProcessName, request.ProcessName, OrdinalIgnoreCase)` ⇒ `null` 与 `""` 不等 |
| E13 | `DefaultCmdExecute`（主A/兜底两处绑定） | 传入的进程名来自 `Tool.RemoteViewProcessName`，未配置即 `null` |
| E14 | `VncViewer.BindWindowOnStationAsync`（改前） | 回绑体 `{processId, processName, sessionKey: null}`，`ProcessName` 来自地址栏 ⇒ 空串 |
| E15 | `ProcessEditor.razor` 的 `VncPidReady` 处理 | `dedupKey = sessionKey ?? $"{stationIp}\|{pid}\|{processName}"` ⇒ 两次通知键**形状不同** |
| E16 | `WindowBindRegistry.SetTarget` | `sessionKey` 为空串/null 时**保留**旧会话键 ⇒ 日志里回绑仍显示 `会话=fc56`，容易误读为"同会话" |

## 4. 修复设计（决策记录）

| # | 决策点 | 拍板结果 | 理由 |
|---|---|---|---|
| D1 | Elsa 身份通道怎么修 | **改用管理员 JWT**（与 Studio 同源：`ElsaAdminCredentialResolver` 派生凭据 → `POST {engine}/elsa/api/identity/login`） | JWT 通道**已被实测证明可用**（§2.1 E4/E5）且 Studio 一直走它；ApiKey 方案需要在引擎显式引导一把密钥并让 DispatchServer 同源返回，属另一条路、收益相同 |
| D2 | 不用 `UseDevelopmentAdminApiKey()` | **不采用** | 官方文档明写 *Do not use in production*，与本仓「拒绝已知公开默认值」的既有口径（`ElsaSigningKeyResolver` 注释）冲突 |
| D3 | 登录实现放哪 | **`DelegatingHandler`**（`ElsaJwtAuthHandler`）挂在 `ElsaApiClient` 自己的 HttpClient 上 | 一处生效，`ElsaApiClient` 十几个方法零改动；登录用**自带裸 HttpClient** ⇒ 不会递归回调本 handler |
| D4 | 令牌生命周期 | 进程内静态缓存 + 按 JWT `exp` 提前 2 分钟续期；读不到 `exp` 退 30 分钟 | 每进程只登录一次；引擎重启换签名密钥也能自愈 |
| D5 | 401 处理 | 强制重登并**重发一次**（仅当请求体是可重复读的内存态内容：`JsonContent/StringContent/ByteArrayContent/FormUrlEncodedContent`） | 过期/换密钥时透明恢复；流式/多部件不重放，避免半截发送 |
| D6 | 登录失败 | 不长期缓存，只做 **5s 退避** | 引擎后起可自愈，又不至于每个请求打两次登录 |
| D7 | 失败可观测性 | `SaveWorkflowAsync` / `ExecuteAsync` 非 2xx（或无实例 ID 头且非 cannot-start）**抛带状态码与响应体的可读异常**；`GetJournalAsync` 空实例 ID 直接返回空 | 消灭"假 404 掩盖真因"这类事故，下一次引擎侧拒绝会直接说清楚 |
| D8 | VNC 双弹窗怎么修 | ①`WindowBindRequest` 新增 `Notify`（默认 true），VncViewer 回绑传 **false**（只绑定、不通知）；②进程名判据改 `(x ?? "")` **空值等价**比较 | ①从语义上根除"回绑=新可视化需求"的误判；②双保险，且不改变 StationAgent 路径的默认行为 |
