
### 4.2 风险（**2026-10-30 取证后更正，原判断有误**）

> **⚠ 原稿此处写「照抄现有写法会立刻造成可见性回归」——该判断不成立，已作废。**
> 取证：`CJCore/src/Framework/CJCore.Framework.UI/ModuleAccessRouteView.cs:183-196`，
> `AuthorizeAsync` 只把 `moduleAccessAttr.AccessKey` 塞进 `PermissionContext` 交给
> `PermissionRouter.EvaluateAsync`，**`DefaultRoles`（第二参数）从未被读取**。
> 角色口径由统一鉴权中心（声明 Roles / `ModuleAccessOptions` / 权限矩阵）决定，特性第二参数**当前不生效**。

既有 11 页、共 7 个键，写法**全部**是：

```csharp
@attribute [CJCore.Framework.Abstractions.ModuleAccess("plug-guacamole", "system_admin")]
```

**仍然建议把这 11 处的 `"system_admin"` 改成 `"*"`，但理由是防御性而非救火**：
第二参数现在是死参数，改了不影响任何当前行为；可一旦框架将来开始读它（它已在
`ModuleAccessAttribute.DefaultRoles` 上定义好、`GetDefaultRoleArray()` 也写好了），
这 11 处会**突然把非管理员关在门外**且毫无预警。现在改掉 = 拆掉一颗定时地雷，成本为零。

**真正的可见性变化点（B-2 唯一会改变使用者体验的地方）**：

页面一旦声明 `[ModuleAccess(key)]`，就开始查 `PermissionRouter`，而它的角色来源是
**`IModuleAccessDeclaration` 的 `Roles`**。13 个待补页面所引用的键里，有 **2 个是 `["system_admin"]`**：

| 页面 | 键 | 声明 Roles | 补键后的变化 |
|---|---|---|---|
| `/JobManageList` | `plug-job-manage` | `["system_admin"]` | 非管理员**菜单本就看不到**；补键后直连 URL 也被拦 ⇒ 与菜单口径自洽 |
| `/ProcessManageList` | `plug-process-manage` | `["system_admin"]` | 同上 |

其余 11 页引用的键（`plug-fmd` / `plug-knowledge` / `plug-model-manage` / `plug-market` /
`plug-skills-manage` / `plug-station` / `plug-tool-resource` / `plug-unit-test` / `plug-ai` /
`plug-process-edit`）声明均为 `["*"]` ⇒ **补键前后可见性完全一致**。

> **处置：接受这 2 页的收紧，不改声明。** 理由：「菜单看不见但直连能打开」本身就是 B 批次要堵的洞，
> 收紧后与菜单口径自洽。若业务上确实要求非管理员能用作业/流程管理，应另起决策点把这两条声明改成 `["*"]`
> （那会同时把菜单放给非管理员，是**放宽**而非收紧，方向相反）。

### 4.3 验收判据

1. 非管理员账号（或模拟 `role != system_admin`）逐个打开 13 个页面，**不出现**「无权访问该页面」；
2. 在模块管理页关掉某模块 → 直连其页面 URL → 命中「无权访问该页面」（注意是 **200 + 正文**，不是 403）；
3. 权限矩阵（`/admin/modules` → 权限页）能看到 13 个新键，且分组名显示为模块中文名而非机器串。

## 5. B-3：34 个 MapGroup（高风险，建议与 D9 合并）

### 5.1 现状

`grep "MapGroup("` = **34 处**，其中 `RequireModuleAccess` **实调用 1 处**（`/api/plug-agent/tools`，
另 1 处是注释）。几乎全部业务端点未声明。

### 5.2 为什么最危险

- 菜单与页面只是"可见性"；API 是**运行时依赖**。键写错 ⇒ 现象是"菜单在、页面开得开、数据全空/报错"，排查成本最高。
- 每个接口键必须配 `pairedWith`（声明"本接口是某页面的运行必需依赖"），否则矩阵里勾页面不勾接口 ⇒ 无提示 403。
- **已知陷阱**：端点一旦带 `RequireAuthorization` 元数据，必须同时进 `NeedsIdentity()` 的 ① 分支，
  否则 EndRequest 阶段抛异常 ⇒ **恒定 500**（P6.3 同类坑，历史上踩过一次）。

### 5.3 致命前提：26 个模块 API 项目**零 CJCore 引用**

实测 `grep CJCore` 于 `JobManageApi` / `KnowledgeManageApi` / `ToolResourceApi` 等 csproj ⇒ **全空**。
而 `RequireModuleAccess` 定义在 `CJCore.Framework.Api`。也就是说 §5.1 的"逐个补键"根本无从下手 ——
必须先给每个业务 API 项目加框架引用，等于**把框架依赖扩散进全部业务项目**。

由此引出 **D-B-3** 三个选项（用户拍板 **A**）：

| 选项 | 做法 | 评价 |
|---|---|---|
| **A（选定）** | **宿主侧集中门控**：唯一宿主加一个中间件，按**端点 Tag** 映射模块键，模块停用 ⇒ 403 | 业务项目**一行不改**、零依赖扩散；代价是权限矩阵看不到接口键（只做启停门控，不做角色判定） |
| B | 给 26 个 csproj 加 `CJCore.Framework.Api` 引用 + 26 处 `RequireModuleAccess` | 标准做法、矩阵可见、`pairedWith` 提醒齐全；但依赖扩散 + 26 文件回归面 |
| C | 缓做，与 D9 全量权限矩阵合并 | 本轮拿不到"关模块 API 也拒" |

### 5.4 A 的实际实现（已落地）

新增 `src/WebHost/CJPlug.Server/../CJ.Plug.HostWebServer/ModuleApiGate.cs`：

1. **用端点 Tag 而不是路径前缀做映射** —— 关键：`/api/plug` 被**三个模块共用**
   （插头执行 / 插头市场 / 插头管理），按路径无法区分归属；而每个 `MapGroup(...)` 都调了
   `WithTags(...)`，Tag 是天然模块身份，且**无需改动任何模块代码**即可读（`ITagsMetadata`）。
2. **未命中映射表一律放行**（保守）：映射遗漏的后果是"该拦的没拦"，而不是"误伤在用接口"。
3. **只做启停门控**，不做角色判定 —— 角色由统一鉴权中心负责，不重复实现。
4. 三档模式 `ModuleApiGate:Mode` = `Off` / `Observe`（只记日志）/ **`Enforce`**（403，已设为默认）。
5. 挂载点 `Program.cs` 中 `UseRouting()` **之后**（依赖 `ctx.GetEndpoint()`）。

> **⚠ 与 §5.2 写的关系**：原以为要动 `NeedsIdentity()` ①分支；选 A 后**完全不需要** ——
> A 不引入 `RequireAuthorization` 元数据，因此不存在"缺授权中间件 ⇒ 恒 500"的陷阱。
