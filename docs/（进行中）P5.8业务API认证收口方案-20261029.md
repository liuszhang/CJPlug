### 1.2 为什么不能"直接给 `/api/*` 加认证"

内部调用方**全部零凭证**：

| 调用方 | 凭证情况 | 规模 |
|---|---|---|
| Blazor Server 的 `MainApiClient`（299 处 `AuditLogHelper` + 全部模块 API） | 构造函数裸 `new HttpClient{BaseAddress=MainApiServer}`，**无任何头** | 53 个 `AddHttpClient` 注册点 |
| `ElsaApiClient` | 同上（`ElsaJwtAuthHandler` 存在但未被 `AddHttpClient` 串上） | — |
| 工位机 `StationApiServer` | 跨进程 HTTP 调 `StaticData.MainServerUrl`，无凭证 | `Program.cs:61-77` |
| 外部 MCP 客户端 | 无凭证（协议层未做鉴权） | — |

⇒ 一旦给 `/api/*` 加 `RequireAuthorization()`，**全站功能立刻断**（首页统计、作业列表、插头市场、执行引擎全部 401）。

## 2. 三个候选方案

### 方案 A　内部信任密钥（Internal API Key）

```
服务端出站：DelegatingHandler 自动加 X-Internal-Key: <配置密钥>
服务端入站：AuthenticationHandler 识别该头 → 生成 principal(internal)
/api/* 端点：RequireAuthorization()
```

| 维度 | 评价 |
|---|---|
| 改动量 | **小** —— 1 个 `DelegatingHandler` + 1 个 `AuthenticationHandler` + `NeedsIdentity`/端点约定各 1 处；**不动 299 处调用点** |
| 安全性 | 中 —— 挡住"无密钥的外部访问"（含同网段）；密钥泄漏=全开 |
| 用户级授权 | ❌ 无法区分用户（内部身份只有一个） |
| 审计粒度 | 现状（`AuditLogHelper` 自己带 userName 字段），不受影响 |

### 方案 B　Bearer 透传（用户级）

把 circuit 的 `accessToken` 注入每次出站请求。

| 维度 | 评价 |
|---|---|
| 改动量 | **大** —— `MainApiClient` 是 Singleton，拿不到 circuit 级 token；要么改 299 处调用点签名，要么用 `AsyncLocal` 传递（隐式上下文，难排查） |
| 安全性 | 高 —— 真正的用户级授权 + 可审计 |
| 跨进程 | 工位机仍需额外 token 交换（与 D-P5-7 的 ExecuteApp 是同一类问题） |

### 方案 C　分层最小收口（**已采纳**）

分三步，每步独立可验收：

| 步骤 | 内容 | 风险 | 状态 |
|---|---|---|---|
| **C2 地基**（**实际第一步**，见下） | 出站自动附加内部密钥 + 入站闸门（Observe 只统计） | 低 —— 零行为改变 | ✅ **已完成（2026-10-29）** |
| **C1** | 只对**写操作**端点收口（POST/PUT/DELETE + 显式 `RequireModuleAccess`），读端点保持匿名 | 低 —— 只影响写 | 待做（前置：工位机密钥下发） |
| **C2 全量** | `GateMode=Enforce` 覆盖全部 `/api/*`，`/mcp`、`/elsa/api/*` 显式保持匿名（既有口径） | 中 —— 需 Observe 覆盖率 100% 且工位机已带密钥 | 待做 |
| **C3** | 外部访问白名单（按 IP/网段），非白名单一律拒绝 | 低（配置层） | 待做（与 D-P5-10 合并） |

### ⚠ 顺序修正（实施时发现，推翻原文档的 C1→C2 排序）

原方案把「C1 写操作收口」排在「C2 内部密钥」前面，**这是不可执行的**：
C1 一旦生效，任何漏串 handler 的内部 HttpClient 调用立刻 401 —— 而"有没有漏"在密钥机制落地前**根本无法度量**。

正确顺序必然是：

```
① 出站全部带密钥（不强制）        ← 本轮 C2 地基
② Observe 跑一轮，量出漏网清单     ← 本轮已做（实测 106/106 = 100%，零漏网）
③ 逐个补齐漏网调用方 + 工位机密钥下发
④ Enforce（先写操作 = C1，后全量）
⑤ C3 IP 白名单
```

这也解释了为什么 §6 实测能一次通过：`IHttpMessageHandlerBuilderFilter` 一个注册点覆盖了全部
53 个 `AddHttpClient`，剩下要手工处理的只有裸 `new HttpClient()`（全仓 24 处，实际打到本站的更少）。

## 7. C1 实施：EnforceWrite 档 + 工位机接入（2026-10-29 深夜）

> 在 C2 地基之上，把「只拦写操作」变成可运营配置，并把工位机侧的出站调用接入密钥。

### 7.1 闸门新增第四档：`EnforceWrite`

| 档位 | 读（GET/HEAD/OPTIONS/TRACE） | 写（POST/PUT/DELETE/PATCH） | 用途 |
|---|---|---|---|
| Off | 放行 | 放行 | 完全关闭 |
| Observe（默认） | 统计 | 统计 | 度量漏网 |
| **EnforceWrite（推荐上线档）** | 统计 | **401** | 关掉"外部能改数据" |
| Enforce | **401** | **401** | 全量收口 |

**为什么需要中间档**：全量 Enforce 的爆炸半径包含所有只读调用方（工位机拉工具列表/下载部署包等），
漏接 handler 就静默变空表；而写操作几乎全部来自本站电路，漏网立刻可见（操作失败有提示）。
EnforceWrite 用最小爆炸半径先关掉最危险的通道。

**统计同步拆成读写两维**（`GateSnapshot.ReadCoverage / WriteCoverage`），缺密钥样例键带 `R:`/`W:` 前缀 ——
同一路径读写混合时，"写不达标"不会被读侧高频成功掩盖。诊断端点分别给出 `write` / `read` 两个对象。

**配置笔误保护**：`GateMode` 拼错（如 `EnforcWrite`）退化为 Observe 而不是 Enforce —— 绝不因笔误全站 401。

### 7.2 工位机侧接入（CJ.Plug.StationApiServer）

- `Program.cs`：`InternalApiKey.Configure(builder.Configuration["InternalApi:Key"])` —— 与主服务同一把钥匙，经 `InternalApi__Key` 环境变量下发；空 = 机制关闭。
- `StationApi.cs` 两处裸 `new HttpClient`（拉工具列表 15s / 下载部署包 30min）→ `InternalApiKey.CreateClient()`；**按端口判定本站**，外部镜像站不会收到密钥头。
- 工位机没有 `AddHttpClient` 注册点 ⇒ 不需要 Filter；`MainApiClient` 经 `BaseApiClient` 的裸实例已接。
- `StationHubService._httpClient` 是**未使用的死字段**（SignalR 自建连接，不受影响），不动。

| **D-P5-10** | 是否收窄监听地址 | **A（保持 `http://*:5066` 全网卡）** —— 用户 2026-10-29 拍板。理由：多网卡/多网段现场部署形态不确定，收窄监听一旦选错网卡会直接断掉工位机与客户端连接，属于"部署期不可远程修复"的故障。<br>**⚠ 连带后果（必须补偿）**：不收窄监听 ⇒ **C3 IP 白名单从"可选加强"升级为"必做补偿控制"**，否则同网段任何主机仍可直连业务 API（`Enforce` 只解决"有没有凭证"，不解决"谁在连"）。C3 建议默认值：仅允许 `127.0.0.1` + 部署期配置的受信网段，非白名单直接 403 且不计入统计（避免污染覆盖率）。 |

### 8.1 D-P5-10 = A 后的风险接受声明

- **接受**：服务继续监听全部网卡，任何可达 5066 的主机都能建立 TCP 连接。
- **不接受**：该主机能改写业务数据 ⇒ 已由 `EnforceWrite` 拦截（本轮完成）。
- **待补**：该主机能**读取**业务数据（`Observe`/`EnforceWrite` 下读侧放行）⇒ 由 C3 白名单 + 全量 `Enforce` 共同解决。
- **判据**：C3 上线前，本项风险等级记为 **中**（内网可达性为前提）；C3 上线后降为 **低**。
