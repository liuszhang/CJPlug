## 1. 背景（机制已实测，不再重复调研）

三面消费方与门控语义（均已实测验证，证据见附录 T.7）：

| 面 | 消费点 | 代码位置 | 判定方式 |
|---|---|---|---|
| 菜单 | `CoreMenu` → `MenuVisibilityRules.IsVisibleAsync` | `CJCore.Framework.UI/Components/MenuVisibilityRules.cs:33` | 有 `AccessKey` 走策略路由；无 `AccessKey` 走菜单自带 `Roles`（null/空 = 仅登录） |
| AppBar | `IsAppBarItemVisible` | `CJCore.Framework.UI/FrameworkLayout.razor:256` | 直接查闸门 `IsAccessKeyEnabled(key)`，**不做角色判定** |
| 页面 | `ModuleAccessStrategy.EvaluateAsync` **第 0 步** | `CJCore.Modules.Permission.Api/Services/ModuleAccessStrategy.cs:62` | 门控先于 `AdminRoles` 硬保护（管理员同样受约束） |

闸门的唯一数据源（**这是全部问题的根源**）：

```
DefaultModuleCatalog.IsAccessKeyEnabled(key)          // 行 128
  └─ _accessKeyIndex.TryGetValue(key, out location)
       未命中 ⇒ return true（放行，静默）
  └─ _accessKeyIndex 只从 module.Features 建
  └─ module.Features 只收 IsSameModule(moduleId, moduleName, entry.Owner) 为真的键
  └─ entry.Owner 只来自 IModuleAccessDeclaration.ModuleName
```

**两条硬结论**（决定本方案的形状）：

1. **只给菜单加 `AccessKey` 而不注册声明 = 白加**（`Owner=null` 进不了索引，闸门直接放行）。
2. **声明 `AccessKey` 与 `Module.ModuleId` 逐字一致时**，该键即"模块级功能项"，关模块就关它。

## 4. 不做的事（上一轮说过的"顺带修正"已作废，理由在此）

上一轮我提议"把现有 11 条声明的 `ModuleName` 从中文名改传 `moduleId`"。**核实后该提议作废**，但作废的**理由要精确**（原写法过粗，已按实测数据修正）：

矩阵分组名 `moduleName` 的计算是 `ResolveGroupName(a) = FirstNonEmpty(a.MenuGroup, a.ModuleName)`
（`PermissionFunctionsService.cs:446`，2026-10-21 口径"矩阵分组 = 左侧导航分组，而不是各模块自报的模块名"）。即：

| 键的类型 | 分组名取自 | `ModuleName` 改传 `moduleId` 的后果 |
|---|---|---|
| **有菜单**的键（本方案 8 个） | 菜单的 `GroupName`（如"通用""调试"） | 不显示、不影响、无收益 —— 改了纯粹是噪音 |
| **无菜单**的纯声明键（`plug-ai`、`plug-guacamole`） | 回落 `declaration.ModuleName` | **矩阵分组会变成 `plug-ai` 这种机器串**（实测 `plug-ai` 分组显示为"AI 助手"，正是来自这条回落） |

**结论**：`ModuleName` 保持与 `Module.Name` 逐字一致（中文显示名），不改传 `moduleId`。真正的锚点是 `IsSameModule(moduleId, moduleName, Owner=ModuleName)` 的逐字相等，改名脆性由双向包含兜底一半。

**替代方案（本方案采用）**：不做代码改动，改为**约定 + 验收断言**——

1. `ModuleName` 必须与 `Module.Name` 逐字一致（写进 §3.2 的注释模板）；
2. 验收脚本断言：`/api/modules/` 返回的每个模块，凡 `features` 里出现 `featureKey == moduleId`，其 `name` 必须等于该模块的 `name`（漂移自动暴露）。

> 若你希望把它做成运行时告警（闸门查询未命中索引时 `LogWarning`），那是 CJCore 侧改动，属于独立议题，本方案不掺。

## 5. 待拍板：D-P6-4 新声明的角色白名单口径

这是**唯一**未定项。新增的 9 条声明若带 `Roles`，会立刻影响"谁能看见"——因为策略链第 4 步就是"默认模式声明"。

### 选项

| 选项 | 写法 | 可见性变化 | 与现状关系 |
|---|---|---|---|
| **A（推荐）** | 全部 `Roles = ["*"]` | **零变化**：所有登录用户仍看到这 8 个菜单 + AskAI | 与当前"无 `AccessKey` = 仅登录"完全等价，只多出"可被模块启停关掉"的能力 |
| **B** | 全部 `Roles = ["system_admin"]` | **收窄**：非管理员登录后，这 8 个菜单 + AskAI **全部消失** | 与既有 11 条声明写法一致，但等于顺手做了权限收窄 |

### 推荐 A 的理由

1. **本方案的验收判据是"启停可见"，不是"权限分层"**。把可见性一起改了，一旦操作员反馈"菜单没了"，无法区分是启停 bug 还是权限收窄——两个变量同时动，违反"一次只动一个变量"。
2. `"*"` 在框架里是**一等公民**，不是 hack：`ModuleAccessStrategy.Decide` 显式支持 `roles.Contains("*")`，注释写明"公共项（所有已登录用户都算命中）……见 CJOntology `HomeUiModule`"，已有先例。
3. 门控在第 0 步、角色在第 4 步，**两者正交**：用 `"*"` 不妨碍"关模块能把入口关掉"，这正是 P6.4 要的能力。
4. 角色收窄应该跟**页面/API 一起做**（B 选项 + D9 权限矩阵同批），否则会出现"菜单只有管理员看得见、但页面直达谁都进得去"的更糟形态（当前 153 页只有 11 页带 `[ModuleAccess]`）。

### 若选 B 的必然后果（请一并确认）

`plug-knowledge`、`plug-market`、`plug-station`、`plug-tool-resource`、`plug-skills-manage`、`plug-model-manage`、`plug-fmd`、`plug-unit-test` 这 8 个入口对**非 `system_admin` 角色立即不可见**，而对应页面（无 `[ModuleAccess]`）仍可直达。这是**不一致**，需要 B/C 批次补齐才能收敛。
