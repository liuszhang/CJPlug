## 2. 根因（实测证据链）

**根因一句话**：Elsa 3.9 把「内置管理员用户 / 内置管理员 API Key / localhost 自动放行」三条引导路径**全部改成必须显式配置**，而 CJPlug 的三处调用都写成了「参数为空 = 不启用」，导致 **Elsa 引擎侧不存在任何可用凭据**；同时 Studio 侧的令牌从来没产生过 ⇒ Studio 对引擎的每个请求都是匿名 ⇒ **401**。

### 2.1 现场实测（对运行中的安装态取证）

| # | 证据 | 实测值 |
|---|---|---|
| E1 | `GET http://localhost:5001/elsa/api/descriptors/activities`（**正是** `RemoteActivityRegistryProvider` 调的那支） | **401**，响应头 `WWW-Authenticate: Bearer` |
| E2 | `GET http://localhost:5001/elsa/api/workflow-definitions` | **401** |
| E3 | `POST http://localhost:5001/elsa/api/identity/login`，体 `{"username":"admin","password":"password"}` | **200** + `{"isAuthenticated":false}`（**引擎里没有这个账号**） |
| E4 | 监听端口 | `5001`(ElsaApiServer) / `5066`(HostWebServer) / `8686` / `8687` / `3001` 均在；`5010`(ElsaStudio 独立站) 未起 |
| E5 | 安装形态 | `CJ.Plug.Desktop.exe` → Aspire AppHost → 8 个服务，全部 `AddExecutable("dotnet", servicesDir, "<服务>.dll")`（**同一工作目录**） |

### 2.2 源码级证据（Elsa 3.9.0，commit `6436609a…` 原文核对）

| # | 证据 | 结论 |
|---|---|---|
| E6 | `IdentityFeature.UseAdminUserProvider()`（无参）+ `AdminUserProviderOptions.UserName/Password` 默认 `""` | **未显式配置 = 该 provider 拒绝一切用户**。程序集文案：*"Use the options-based constructor. The built-in admin user is disabled unless explicitly configured."* |
| E7 | `DefaultAuthenticationFeature.UseAdminApiKey()`（无参）+ `AdminApiKeyOptions.ApiKey` 默认空 | **未显式配置 = 该 provider 拒绝一切 key**。文案：*"The built-in admin API key is disabled unless explicitly configured."* |
| E8 | `IdentityBootstrapDiagnostic`（3.9 新增的启动自检） | 注释原文：*"This replaces the localhost permission grant that used to ride on the SecurityRoot policy. That grant trusted network position … **and it granted unauthenticated access**"* ⇒ **3.9 起 localhost 不再自动放行**；这正是「升级前好用、升级后全 401」的分水岭。同一自检会在无引导时打红字：*"No users exist and no identity bootstrap is configured, so nothing can sign in and every management endpoint will answer 403…"* |

| E12 | `UserManager.CreateUserAsync` 只 `Trim()` 后哈希，**无口令复杂度/长度校验** | 派生口令（Base64，无空白）可直接作为种子口令 |

## 3. 影响面（不止「组件库」）

401 打掉的是 **Elsa Studio → 引擎的整条通道**，以下能力**当前全部静默失败**（只是没像组件库那样立刻可见）：

| 能力 | 代码路径 | 后果 |
|---|---|---|
| 组件库列表 | `RemoteActivityRegistryProvider` | P1 空白 |
| 画布加载（Mapper） | `MapperFactory` → 同一支描述符调用 | P2 堆栈；画布能画但映射器建不起来 |
| 流程保存 / 发布 | `ElsaStudioService.SaveAsync` / `CreateOrUpdateWorkflowFromProcess` | 保存到引擎失败 |
| 流程执行 | `ExecuteWithCorrelationIdAsync` → `WorkflowDefinitionService.ExecuteAsync` | 执行失败（含 MCP 工作流路径） |
| 实例 / 日志 | `GetWorkflowInstanceByCorrelationId` / `GetJournalAsync` | 查询失败 |

> 也就是说：**「画布能画、保存与执行其实一直没成功」**，组件库空白只是最先被看见的那个症状。

### 4.1 目标

1. Elsa 引擎侧**显式引导一个管理员**，并把 `IdentityBootstrapDiagnostic` 的红字**真正消掉**（不是靠加白名单滤日志）；

## 6. 详细设计

### 6.1 服务端：显式种管理员

落点 `CJPlug\src\modules\Integrations\CJ.Plug.ElsaIntegration\ElsaExtensions.cs:72-79`：

```csharp
elsa.UseIdentity(identity =>
{
    identity.TokenOptions = options => options.SigningKey = ElsaSigningKeyResolver.Resolve(configuration);

    // 3.9 起内置 admin 用户/内置 API Key 均默认关闭（未显式配置 = 全拒），且 localhost 不再自动放行。
    // 此处显式种一个管理员：AdminUserInitializer 幂等写 MemoryRoleStore/MemoryUserStore。
    identity.UseDefaultAdmin(admin => admin
        .WithAdminUserName(ElsaAdminCredentialResolver.ResolveUserName(configuration))
        .WithAdminPassword(ElsaAdminCredentialResolver.ResolvePassword(configuration))
        .WithAdminRoleName(ElsaAdminCredentialResolver.AdminRoleName)
        .WithAdminRolePermissions(ElsaAdminCredentialResolver.AdminRolePermissions));

    // ⚠ 原 identity.UseAdminUserProvider(); 必须删除（见下）
});
```

**为什么必须删 `UseAdminUserProvider();`**（这是本方案最容易做错的一步）：
`IdentityFeature.UserProvider` 是**单一委托**，默认 `StoreBasedUserProvider`。调用 `UseAdminUserProvider()` 会把它换成 `AdminUserProvider`——而其选项为空时**任何用户都查不到**。于是 `DefaultUserCredentialsValidator`（它只经由 `IUserProvider` 查人）**永远看不到**刚被 `AdminUserInitializer` 种进 `MemoryUserStore` 的管理员 ⇒ 登录依旧 `isAuthenticated:false`。删掉该行即恢复默认的 store-based provider，种子用户才可解析。

`elsa.UseDefaultAuthentication(auth => auth.UseAdminApiKey());`（`:82`）**不动**：不配 key 即不启用该通道，保持现状。

### 6.2 凭据解析器（C2）

新增 `CJPlug\src\modules\Integrations\CJ.Plug.ElsaIntegration\ElsaAdminCredentialResolver.cs`（`internal static`，风格与 `ElsaSigningKeyResolver.cs` 一致）：

| 档位 | 用户名 | 口令 |
|---|---|---|
| ① 环境变量 | `CJPLUG_ELSA_ADMIN_USER` | `CJPLUG_ELSA_ADMIN_PASSWORD` |
| ② 配置键 | `Elsa:AdminUser` | `Elsa:AdminPassword` |
| ③ 派生（默认） | `admin` | `Base64(SHA256("CJPlug.Elsa.Admin|" + ElsaSigningKeyResolver.Resolve(configuration)))` |

要点：

- **为什么两侧必然一致**：两侧都在同一台机、同一输出目录，`ElsaSigningKeyResolver` 已经保证签名密钥收敛（§9.7：临时文件 + `Move` 覆盖 + 回读）；口令是它的**纯函数**，因此**不存在第二个收敛点**，也不存在"两个文件各写一把"的竞态。
- **为什么失败模式更好**：若签名密钥真的没收敛，JWT 校验本来就炸（响亮失败），不会退化成"登录悄悄 401"这种难查症状。
- **域分隔**：固定前缀 `"CJPlug.Elsa.Admin|"`，与签名用途分开（KDF 域标签），避免"同一串字节两用"。
- **强口令**：SHA256 → Base64 = 44 字符（256 bit 熵源），远超任何策略（且 Elsa 本无策略，见 E12）。
- **不打印口令**：只打印「口令来源：环境变量 / 配置键 / 由签名密钥派生」+ 用户名。

### 6.3 客户端：`CjElsaAutoLoginJwtAccessor`（A3）

新增 `CJPlug\src\modules\Integrations\CJ.Plug.ElsaIntegration\CjElsaAutoLoginJwtAccessor.cs`：

```csharp
internal sealed class CjElsaAutoLoginJwtAccessor(
    IHttpClientFactory httpClientFactory,
    IRemoteBackendAccessor remoteBackendAccessor,
    IConfiguration configuration) : IJwtAccessor
{
    private readonly Dictionary<string, string> _tokens = new();
    private readonly SemaphoreSlim _gate = new(1, 1);

    public async ValueTask<string?> ReadTokenAsync(string name)
    {
        if (_tokens.TryGetValue(name, out var cached)) return cached;
        await EnsureLoggedInAsync();
        return _tokens.GetValueOrDefault(name);
    }

    public ValueTask WriteTokenAsync(string name, string token)
    {
        _tokens[name] = token;      // 刷新流程（ElsaIdentityRefreshTokenService）写回此处
        return ValueTask.CompletedTask;
    }
    // EnsureLoggedInAsync：单飞 → 用裸 HttpClient POST {Backend.Url}/identity/login
    //   {"username":…, "password":…} → 复用 Elsa.Api.Client 的 LoginRequest/LoginResponse
    //   成功缓存 accessToken/refreshToken；失败**不缓存**（下次请求自动重试）
}
```

时序（为什么无竞态、无递归）：

```
Studio 任一消费者（HTTP handler / SignalR / AuthenticationStateProvider）
  └─ IJwtAccessor.ReadTokenAsync("accessToken")        ← 我们的实现
       └─ 未命中 → 单飞
            └─ 裸 HttpClient（无 Elsa 认证 handler）POST {Backend.Url}/identity/login
                 └─ 返回 accessToken/refreshToken → 缓存
       └─ 命中后返回令牌 ⇒ 认证 handler 附 Bearer
```

- **无递归**：登录请求走 `CreateClient()` 默认客户端（未挂 `AddHttpMessageHandler`），**不会**再次进入 `AuthenticatingApiHttpMessageHandler`，因此不会回调 `ReadTokenAsync`。
- **无竞态**：令牌由首次 `ReadTokenAsync` 惰性取得，早于任何业务请求，不依赖 JS interop、不依赖"哪个组件先渲染"，预渲染期也可用。
- **无循环依赖**：**刻意不复用** `ICredentialsValidator`（`ElsaIdentityCredentialsValidator` → `IBackendApiClientProvider` → 带认证 handler 的 HttpClient），正是为切断递归；此处照抄 `ElsaIdentityRefreshTokenService` 的"裸 HttpClient 打 identity 端点"写法。
- **自愈**：ElsaApiServer 还没就绪导致登录失败时，下一次 `ReadTokenAsync` 会重试；不会把失败结果粘住。

### 6.4 接线

`ElsaExtensions.AddElsaServicesForWeb()`（`:293-324`）内，`AddLoginModule()`（`:309`）**之后**追加：

```csharp
// Studio 的 HTTP/SignalR/登录态三处统一从 IJwtAccessor 取令牌；
// 替换为「内存缓存 + 惰性自动登录」，不再依赖浏览器 localStorage。
```

顺序要求：必须在 `AddLoginModuleCore()/AddLoginModule()`（`:308-309`，注册 `BlazorServerJwtAccessor`）之后，否则会被后注册者覆盖回去。

### 11.2 与评审稿的偏差（4 处，均由实测驱动）

| # | 偏差 | 原因 / 证据 |
|---|---|---|
| **D1** | 客户端注册改用**同程序集工厂**：`ServiceDescriptor.Scoped<IJwtAccessor>(sp => new CjElsaAutoLoginJwtAccessor(...))`，而非 `Scoped<TService,TImpl>()` | 后者要让 DI 反射构造 `internal` 实现类型，跨程序集可见性是隐患；工厂在本程序集内 `new`，零歧义 |
| **D2** | `ElsaStudioService` 构造签名**新增 `IConfiguration`** | 让"配置键"档位在手动登录路径（`LoginToElsaEngine`）也生效，避免与自动登录取到不同口令 |
| **D3** | **枝 2 被推翻**：`UseDefaultAdmin` 与 `UseAdminUserProvider` 不能并存 | 实测日志：`Background task AdminUserInitializer failed with an error` / `System.InvalidOperationException: A role with ID 'admin' already exists.`（`AdminUserInitializer` 与 `AdminRoleProvider` 抢同一角色）⇒ 最终只填 `DefaultAdminUserOptions`（让自检认定"已引导"、消红字）+ 凭据走 provider（请求时校验、不依赖启动链） |
| **D4** | `CJActivityProvider` 顺带修复（原不在改动面） | F4 冷启动实验证明：它抛异常会打崩 tenant 启动任务链，连带跳过身份引导。改 `async` + **降级返回空**，不打崩链条 |
| **D5** | `CJActivityProvider` 需类型别名 `PlugEntity` | 本文件命名空间链上有 `CJ.Plug` 这个**命名空间**，显式声明 `List<Plug>` 会被解析成命名空间（`CS0118`）；`async` 化后 `return new(activities)` 也被 target-type 成接口（`CS0144`）⇒ 改别名 + `return activities` |
