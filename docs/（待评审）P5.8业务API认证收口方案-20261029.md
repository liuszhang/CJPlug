## 1. 现状取证（2026-10-29 22:00 实测）

### 1.1 认证覆盖矩阵

| 面 | 路径 | 认证 | 证据 |
|---|---|---|---|
| 页面 | 全部 Blazor `@page` | ✅ 已收口（P5.5 两批） | 匿名 → 302 `/three-role/login` |
| 三员 API | `/api/three-role/*` | ✅ | 无 token → 401 |
| 个人中心 | `/api/personal-center/*` | ✅ | 同上 |
| CJCore 管理 | `/api/module-admin`、`/api/system-config` | ✅ | `NeedsIdentity` 显式 true |
| **业务 API** | `/api/*`（其余全部） | ❌ **匿名** | `NeedsIdentity` 返回 false ⇒ 不挂授权中间件 |
| **MCP** | `/mcp` | ❌ 匿名 | 同上（既有口径） |
| **Elsa 引擎** | `/elsa/api/*` | ❌ 匿名 | 同上 |

### 1.2 为什么不能"直接给 `/api/*` 加认证"

内部调用方**全部零凭证**：

| 调用方 | 凭证情况 | 规模 |
|---|---|---|
| Blazor Server 的 `MainApiClient`（299 处 `AuditLogHelper` + 全部模块 API） | 构造函数裸 `new HttpClient{BaseAddress=MainApiServer}`，**无任何头** | 53 个 `AddHttpClient` 注册点 |
| `ElsaApiClient` | 同上（`ElsaJwtAuthHandler` 存在但未被 `AddHttpClient` 串上） | — |
| 工位机 `StationApiServer` | 跨进程 HTTP 调 `StaticData.MainServerUrl`，无凭证 | `Program.cs:61-77` |
| 外部 MCP 客户端 | 无凭证（协议层未做鉴权） | — |

⇒ 一旦给 `/api/*` 加 `RequireAuthorization()`，**全站功能立刻断**（首页统计、作业列表、插头市场、执行引擎全部 401）。

## 2. 三个候选方案

### 方案 A　内部信任密钥（Internal API Key）

```
服务端出站：DelegatingHandler 自动加 X-Internal-Key: <配置密钥>
服务端入站：AuthenticationHandler 识别该头 → 生成 principal(internal)
/api/* 端点：RequireAuthorization()
```

| 维度 | 评价 |
|---|---|
| 改动量 | **小** —— 1 个 `DelegatingHandler` + 1 个 `AuthenticationHandler` + `NeedsIdentity`/端点约定各 1 处；**不动 299 处调用点** |
| 安全性 | 中 —— 挡住"无密钥的外部访问"（含同网段）；密钥泄漏=全开 |
| 用户级授权 | ❌ 无法区分用户（内部身份只有一个） |
| 审计粒度 | 现状（`AuditLogHelper` 自己带 userName 字段），不受影响 |

### 方案 B　Bearer 透传（用户级）

把 circuit 的 `accessToken` 注入每次出站请求。

| 维度 | 评价 |
|---|---|
| 改动量 | **大** —— `MainApiClient` 是 Singleton，拿不到 circuit 级 token；要么改 299 处调用点签名，要么用 `AsyncLocal` 传递（隐式上下文，难排查） |
| 安全性 | 高 —— 真正的用户级授权 + 可审计 |
| 跨进程 | 工位机仍需额外 token 交换（与 D-P5-7 的 ExecuteApp 是同一类问题） |

### 方案 C　分层最小收口（**推荐**）

分三步，每步独立可验收：

| 步骤 | 内容 | 风险 |
|---|---|---|
| **C1** | 只对**写操作**端点收口（POST/PUT/DELETE + 显式 `RequireModuleAccess`），读端点保持匿名 | 低 —— 只影响写，页面仍走内部密钥 |
| **C2** | 内部密钥（方案 A）覆盖全部 `/api/*`，`/mcp`、`/elsa/api/*` 显式 `AllowAnonymous`（保持既有口径） | 中 —— 需确保所有内部 HttpClient 都串上 handler |
| **C3** | 外部访问白名单（按 IP/网段），非白名单一律拒绝 | 低（配置层） |

---

## 3. 推荐与决策点

**推荐 C**：C2 的"内部密钥"一次解决 53 个注册点的凭证问题（集中串 handler），C1/C3 分批降低爆炸半径；`/mcp` 与 `/elsa/api/*` 保持匿名（既有口径，改动会连带工位机与外部 MCP 客户端）。

### 待拍板

| 编号 | 问题 | 选项 |
|---|---|---|
| **D-P5-8** | 业务 API 收口范围 | **A** 方案 A（内部密钥，一次全收）/ **B** 方案 B（Bearer 透传，用户级但改动大）/ **C** 方案 C（分层，推荐） |
| **D-P5-9** | `/mcp` 与 `/elsa/api/*` 是否同步收口 | **A** 保持匿名（既有口径，推荐）/ **B** 一并加内部密钥（会断外部 MCP 客户端） |
| **D-P5-10** | 监听地址是否收窄 | **A** 保持 `http://*:5066` + 依赖 C3 白名单 / **B** 改绑内网网卡（推荐，产品侧需确认工位机网段） |

## 4. 风险

| 风险 | 说明 | 缓解 |
|---|---|---|
| 收口炸全站 | 任一内部 HttpClient 漏串 handler ⇒ 该模块全 401 | C1 先做写操作；每步跑 P5.5 的 12 页 + 三态冒烟 |
| 工位机断链 | 跨进程无凭证 | 工位机配置里同步下发内部密钥；或用 D-P5-10-B 绑定内网后按 IP 放行 |
| 密钥管理 | 明文配置 | 复用 `ThreeRoleAdmin:AdminPassword` 同款配置位置；信创离线环境下不落地到源码 |
| 与 D-P5-6/D-P5-7 叠 | cookie 会话绑定、ExecuteApp 认证同属"身份传递"族 | 建议 D-P5-6 → D-P5-7 → D-P5-8 顺序做，共用内部密钥基础设施 |

---

## 5. 本阶段不动的东西

- 不改 `NeedsIdentity` 的既有分支（`/api/*` 匿名）
- 不给 `/mcp`、`/elsa/api/*` 加认证
- 不改 299 处 `AuditLogHelper` 调用
