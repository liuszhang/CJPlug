## 0. 结论先行

**先纠正一个判断错误。** 前一版结论把「5 个模块仍在用旧 `IFunctionPermissionProvider`」定性为"死代码，删掉即可"，这是错的。

真相是：**两侧存在两个同名不同版的 `IFunctionPermissionProvider` 接口**，CJPlug 模块注册的是自己那版，而权限矩阵只认 CJCore 那版 —— 结果是这 5 个模块的 **27 个功能点从未进入权限矩阵**，属于**功能缺口**而非技术债。

修复不是"删除"，是"归口"：

| # | 任务 | 文件数 | 性质 |
|---|---|---|---|
| A | 5 个 Provider 改实现 CJCore 版接口 | 5 | 功能缺口修复 |
| B | 4 个模块补 `IModuleAccessDeclaration` | 4 | P6.3 前置（模块可见性） |
| C | 4 个模块菜单补 `AccessKey` | 2 | P6.3（功能键归组） |
| D | 删 CJPlug 版接口定义 | 1 | 收口 |

**一个待拍板决策点**（§4 D1：功能点 Key 是否统一格式）。其余按代码事实现场定死。

## 1. 根因

### 1.1 两个同名接口，字段数不同

| 命名空间 | 文件 | 字段 |
|---|---|---|
| `CJ.Plug.Models.Contracts`（CJPlug 版） | `CJPlug/src/Core/CJ.Plug.Models/Contracts/IFunctionPermissionProvider.cs` | Key / Name / ModuleName / Description / Group —— **5 个** |
| `CJCore.Framework.Abstractions`（CJCore 版） | `CJCore/src/Framework/CJCore.Framework.Abstractions/IFunctionPermissionProvider.cs` | 上述 5 个 + **`ParentKey`** + **`Kind`** + **`Category`** —— **8 个** |

CJCore 版多出的三个字段都有实际用途（2026-10-06 / 2026-10-21 两次演进加入）：

- `ParentKey` —— 权限矩阵多层级树的挂点，按钮挂到所属页面下渲染成子行
- `Kind` —— 可见性类型（`VisibilityKind.Button`）
- `Category` —— 页签维度（可见性 / 数据操作）

### 1.2 消费方只认 CJCore 版

```csharp
// CJCore/src/Modules/Permission/CJCore.Modules.Permission.Api/Services/PermissionFunctionsService.cs:31
private readonly IEnumerable<IFunctionPermissionProvider> _providers;   // ← CJCore 命名空间

// :366  第 4 类数据源
// 4. 手工声明（IFunctionPermissionProvider → 默认可见性/按钮；可显式改判）
foreach (var p in _providers)
    foreach (var item in p.GetPermissions())
    {
        a.ProviderKind     ??= item.Kind;
        a.ProviderCategory ??= item.Category;
        a.ProviderParentKey??= item.ParentKey;
        ...
    }
```

而 5 个 CJPlug 模块的 `ServiceCollectionExtensions.cs` **第一行 using 全部是 `CJ.Plug.Models.Contracts`** —— 注册进容器的是 CJPlug 版接口实例。

DI 按**接口类型**解析：`IEnumerable<CJCore...IFunctionPermissionProvider>` 拿不到任何 `CJ.Plug.Models.Contracts.IFunctionPermissionProvider` 的注册。

⇒ **27 个功能点对权限矩阵完全不可见**。这是编译期就确定的静默失败，无异常、无告警。

### 1.3 CJPlug 侧零消费方

全仓 `grep IFunctionPermissionProvider` 命中 11 个文件，构成：

```
1 个接口定义 + 5 个实现类 + 5 条 AddSingleton 注册语句
```

**没有任何一处注入或遍历**。也就是说这些注册"进去了但没人取"——连错误都不会报。

## 3. 修复方案

### 3.1 任务 A：接口归口（5 个文件）

改造模式（以 ProcessManage 为例）：

```csharp
// 改前
using CJ.Plug.Models.Contracts;                    // ← CJPlug 版

public class ProcessManagePermissionProvider : IFunctionPermissionProvider
{
    public List<FunctionPermissionItem> GetPermissions() => [ ... ];
}

// 改后
using CJCore.Framework.Abstractions;               // ← CJCore 版

public class ProcessManagePermissionProvider : IFunctionPermissionProvider
{
    public string ModuleName => "流程管理";
    public string? ModuleIcon => Icons.Material.Filled.AccountTree;

    public List<FunctionPermissionItem> GetPermissions() =>
    [
        new() { Key = "plug-process:view",   Name = "查看流程", ModuleName = ModuleName,
                Group = "流程管理", ParentKey = "plug-process" },
        new() { Key = "plug-process:create", Name = "创建流程", ModuleName = ModuleName,
                Group = "流程管理", ParentKey = "plug-process" },
        ...
    ];
}
```

**必须补两个字段**：

| 字段 | 取值 | 理由 |
|---|---|---|
| `ParentKey` | 模块级键（如 `plug-process`） | 矩阵据此把按钮渲染成模块行下的子行；不填 = 平铺在根，27 项散落难找 |
| `Group` | 模块显示名 | 按钮类项的悬停提示（`OgaPermissionAdminService.cs:507` 消费） |

`Kind` 保持默认 `VisibilityKind.Button`（手工声明项的历史语义就是按钮位），`Category` 留 `null` 走来源推断（→ 可见性）。

**注册语句不变**（仍是 `AddSingleton<IFunctionPermissionProvider, XxxProvider>()`），因为 using 改了之后 `IFunctionPermissionProvider` 已指向 CJCore 版。

### 3.2 任务 B：补模块级声明（4 个文件）

模式完全照抄已有的 LlmConfig：

```csharp
// CJPlug/src/modules/LlmConfigModule/CJ.Plug.LlmConfig/ServiceCollectionExtensions.cs:31
// P5.5：模块权限声明 —— 供权限矩阵页（/admin/role-permissions）扫描出该键；
//   不注册则矩阵里看不到它，现场无法改角色（只能改代码重编）。
services.AddSingleton<CJCore.Framework.Abstractions.IModuleAccessDeclaration>(
    new CJCore.Framework.Abstractions.ModuleAccessDeclaration("plug-llm-config", ["system_admin"], "LLM 配置"));
```

四个待补：

| 模块 | AccessKey（= `Module.ModuleId` 真值） | ModuleName（= `Module.Name`） | 默认角色 |
|---|---|---|---|
| JobManage | `plug-job-manage` | 作业管理 | `["system_admin"]` |
| PDZManage | `plug-pdz` | 插头数据区(PDZ) | `["system_admin"]` |
| PlugExecute | `plug-execute` | 插头执行 | `["system_admin"]` |
| ProcessManage | `plug-process-manage` | 流程管理 | `["system_admin"]` |

> ⚠ **`AccessKey` 必须以 `Module.ModuleId` 为唯一权威**，不能按 `plug-<模块>` 规则臆造（本方案初稿曾误写 `plug-job` / `plug-process`，实测真值带 `-manage` 后缀，见 §9.2 偏差 1）。
> `ModuleName` 必须取 `Module.Name`，因为 `DefaultModuleCatalog.IsSameModule` 靠它比对归属。

**这三个模块的 AccessKey 同时充当 `ParentKey` 的落点**，所以任务 A 的 `ParentKey` 和任务 B 的 `AccessKey` 必须逐字一致——这是本方案的最高风险点（见 §6 R1）。

### 3.3 任务 C：菜单 `AccessKey`（2 个文件）

| 模块 | 文件 | 动作 |
|---|---|---|
| JobManage | `Menus/JobManageMenu.cs` | 补 `AccessKey = "plug-job"` |
| ProcessManage | `Menus/ProcessManageMenu.cs` | 补 `AccessKey = "plug-process"` |
| PDZManage | **无 `IMenuService` 实现** | 不补菜单；靠任务 B 的 `IModuleAccessDeclaration` 直接提供功能键 |
| PlugExecute | **无 `IMenuService` 实现** | 同上 |

依据 `DefaultModuleCatalog.BuildFeatures()` 的三类来源：

```
功能键目录 = 模块声明 AccessKey + 菜单项 AccessKey + AppBar 项 AccessKey
归属 = 经 IModuleAccessDeclaration 反查；未声明归属的键不参与归组（保持不误伤）
```

⇒ PDZ / PlugExecute 没有菜单项不影响 P6.3 落地，模块声明本身就是一个功能键。

### 3.4 任务 D：删 CJPlug 版接口（1 个文件）

`CJPlug/src/Core/CJ.Plug.Models/Contracts/IFunctionPermissionProvider.cs`

**删除前置**：任务 A 全部完成且编译通过。删除后若仍有引用，编译器会直接报错——这是安全网。

## 4. 决策点 D1：功能点 Key 是否统一格式

### 关键证据：三张权限表全空

```
PM_RoleMenuPermissions  : 0 行
PM_UserPermissions      : 0 行
RoleFunctionPermissions : 0 行
```

（实测 `02.Publish/Services/main.db`）

因为 27 个功能点从未进入矩阵（§1.2），**不存在任何以 `Job.View` 这类键落库的授权数据**。改键名**零迁移成本**。

| 选项 | 形态 | 评价 |
|---|---|---|
| **A：统一为 `plug-<模块>:<动作>`** | `plug-job-manage:view` / `plug-process-manage:create` | ✅ **推荐**。与 CJCore 现行风格一致（`llm:providers` ← `llm:ui:provider-create`）；`ParentKey` 天然等于模块键，层级无需额外映射 |
| B：保留旧格式 `Module.View` | `Job.View` / `Process.Create` | 零改动，但与 CJCore 的 kebab/colon 风格割裂；`ParentKey` 仍要手填模块键，等于混合两套命名 |

推荐 A。选 A 的话，27 个键的完整映射表见附录 A。

### 已定（代码事实可定死）

| # | 结论 | 依据 |
|---|---|---|
| D2 | `Station.View` / `Station.Manage` 暂留 ToolActionSetting | 归属存疑但非阻塞；迁移会牵动 StationManageModule 的键体系，单独议 |
| D3 | `Kind` 不显式指定，用默认 `Button` | 手工声明项历史语义即按钮位 |
| D4 | `Category` 不显式指定，留 `null` 走来源推断 | 推断结果 = 可见性，正确 |
| D5 | 默认角色一律 `["system_admin"]` | 与已完成的 7 个模块一致 |
| D6 | 不新增 `FeatureKey`，直接用 `AccessKey` | `ModuleFeatureSnapshot.AccessKey` 与 `FeatureKey` 同值（`DefaultModuleCatalog.cs:397-398`） |
| D7 | 不注册新的功能键清单类型 | 框架按菜单/AppBar/模块声明三类来源自动推导，无需额外注册 |

### 9.2 与方案的两处偏差（以代码真值为准）

**偏差 1：`ModuleId` 与假设不同**

方案 §3.2 假设为 `plug-job` / `plug-process`，实际代码是：

| 模块 | 方案假设 | **代码真值（已采用）** |
|---|---|---|
| JobManage | `plug-job-manage` | **`plug-job-manage`** |
| ProcessManage | `plug-process-manage` | **`plug-process-manage`** |
| PDZManage | `plug-pdz` | `plug-pdz` ✓ |
| PlugExecute | `plug-execute` | `plug-execute` ✓ |

`AccessKey` / `ParentKey` / `const ModuleKey` 三处全部改用真值。**教训：`AccessKey` 必须以 `Module.ModuleId` 为唯一权威，不能按命名规则臆造。**

**偏差 2：`ParentKey` 未出现在 API 输出**

`FunctionInfoDto` 字段只有 `accessKey / displayName / moduleName / category / visibilityKind / dataGroup`，**不含 `parentKey`**。树形挂载在服务端内部完成，HTTP 侧不可见 —— 所以「矩阵渲染成子行」无法用 curl 断言，只能目检 UI。

### 9.3 顺带修复两个同类存量缺陷（`NeedsIdentity` 缺前缀）

两个 CJCore 管理 API **一直 500**，因为它们声明了 `RequireAuthorization` 却落到 `NeedsIdentity` 的 ② 分支（无授权中间件）：

```
System.InvalidOperationException: Endpoint HTTP: GET /api/permission/functions contains
authorization metadata, but a middleware was not found that supports authorization.
```

| API | 端点前缀 | 修复前 | 修复后 |
|---|---|---|---|
| 权限矩阵 | `/api/permission` | **500** | **200** |
| 模块管理 | `/api/modules`（注意：**不是** `/api/module-admin`，原判断是错的） | **500** | **200** |

**为什么一直没被发现**：两个页面都走 `@inject` 服务注入（`PermissionFunctionsService` / `DefaultModuleCatalog`），完全绕过 HTTP。UI 正常，上游 API 坏的 —— 任何外部集成或自动化验收都会撞上。

修法是在 `NeedsIdentity` 的 ① 清单追加两条前缀（与 P5 时补 `/api/three-role` 同一模式）。

### 9.5 遗留偏差（登记，本次不修）

⇒ IsSameModule("plug-tool-action", "工具动作配置", "插件管理") = false

### 10.4 新发现缺陷（本轮未修，需单独立项）
